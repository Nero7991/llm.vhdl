### What `sqrl_bridge` is (from its own strings, MEASURED)

A JTAG programmer plus a UART-over-TCP multiplexer. Full usage (V1.3.1):

    sqrl_bridge [U] <FTDIindex | L(list) | A(all) | serial-filters
                     | C<ip1>,<ip2>...(CoE devices)>
                    [bitstream.bit | skip, comma-sep for multiple chips]
                    [voltage, comma-sep per board (CoE only)]

Two backends:
- **FTDI JTAG** (the FK33 path): `sqrl_bridge U A sq33_d0006.bit`, after `rmmod ftdi_sio`.
- **CoE = Chip-over-Ethernet** (the JUNGLE CAT path): `sqrl_bridge C<ip1,ip2> sq35_d0006.bit 0.85`.
  The carrier BMC exposes each module's JTAG over TCP; the bridge connects to the
  carrier IP(s), loads the bitstream, and optionally sets VCCINT. It reads DNA,
  USER/USER128 fuses, per-SLR temp and rail voltages, USR_ACCESS, and
  "JungleCat Carrier %i, Module %c, LED RGBABCD" telemetry, and opens a virtual TCP
  serial port per FPGA (what the miner's `--sqrl-hosts 127.0.0.1:200#` connect to).

It links libusb and parses USB descriptors, and TeamRedMiner's FPGA_KASPA_GUIDE names
"the SQRL bridge" as still required for voltage control alongside `--fpga_jc_addr=<IP>`.

### The path to load OUR OWN bitstream on the Jungle Cat (bench work, Oren)

1. Connect the carrier RJ45 to the LAN and power on. Find the carrier BMC IP (DHCP lease
   on the router, or a static default -- unknown, discover it).
2. Load a reference bitstream first as a smoke test:
   `sqrl_bridge C<ip> sq35_d0006.bit` (VCCINT left default until the safe value for this

3. Then load our own standard unencrypted Vivado `.bit` for `xcvu35p` (e.g. the census

## 6. XVC UNLOCKED: Vivado drives JTAG over CoE (MEASURED 2026-09-27, RE result)

Goal: run IBERT on the 16 inter-module GTY pairs. IBERT needs Vivado Hardware Manager
over JTAG (XVC). `sqrl_bridge` contains an XVC server but does not start it in the plain
CoE positional mode. Reverse-engineering found how to enable it.

### The key finding: an UNDOCUMENTED 5th argument is the XVC port

    sqrl_bridge C<ip> <bitstream|skip> <voltage|skip> <XVC_PORT>

MEASURED: `./sqrl_bridge C198.51.100.58 skip skip 2542` prints
"waiting for XVC connection on port 2542", listens on TCP 2542, and answers the XVC
handshake (`getinfo:` -> `xvcServer_v1.0:4096`). The documented usage lists only 4 args;
the 5th (argv[4], `strtol`'d to a port, gated by `argc>4`) is the XVC enable.

How it was found (all static RE of the stripped x86-64 binary, objdump):
- XVC server is `sub_14a60(ctx, uint16 port)`; skips bind if port==0.
- Spawned as a pthread from `sub_140e0`, guarded by a struct field, port from a global.
- The global is `argv[4]` (`[0x23e9c0]`), the gate is `argc` (`[0x23e9c8] > 4`), set in the
  argv parser at 0x497f/0x49ab.
- A DEAD END worth recording: patching the thread's port immediate (file offset 0x81b7,
  `0f b7 77 08` -> `66 be ee 09`) did NOT enable XVC, because the thread is not spawned
  without the 5th arg. The arg is the real switch; do not patch. (`sqrl_bridge_xvc` on the
  BC-250 is that patched copy; it is not needed -- use the original with the 5th arg.)

### Vivado over XVC works (MEASURED)

`connect_hw_server` + `open_hw_target -xvc_url localhost:2542` from Vivado 2023.2 on the
BC-250 enumerates BOTH devices `xcvu35p_0 xcvu35p_1` and reports the loaded census
design's VIO core. So Vivado can drive IBERT/VIO/ILA on either VU35P over CoE.

### CAVEAT: the initial XVC JTAG scan is intermittent

`open_hw_target` fails ~half the time with "No devices detected", then succeeds on retry
(MEASURED: attempt 2-3 of a loop gets `xcvu35p_0 xcvu35p_1`). The bridge's OWN native CoE
scan is 100% reliable, so it is the Vivado-XVC raw-shift path over the tunnel that is
flaky, not the CoE link. WORKAROUND: retry `open_hw_target` 3-8x in the Tcl. Once the
target is open, operations are stable. Likely a TCK-rate/round-trip issue over the tunnel;
lowering TCK or a bridge-side fix is the follow-up. Reading the census VIO for the refclk
was still being stabilized when this was written (Vivado runs timing out on the retries).

## 9. IBERT link test: transceiver refclk is ABSENT on MGTREFCLK0_126 (MEASURED 2026-09-27, ~19:00)

**Question.** Do the 16 differential pairs routed slot-to-slot on the carrier
link up? Loaded a custom IBERT (Quad 126, Custom 1/5 Gbps, QPLL, refclk
`MGTREFCLK0_126` 156.25 MHz, sysclk `QUAD126_0`) on both VU35P modules over the
CoE/XVC path and connected Vivado's hardware manager.

**Answer, up front.** No link, and the reason is upstream of the link: on BOTH
dies the Quad 126 QPLLs are `NOT LOCKED` with `REFCLKLOST=1`, and every GT PMA
reports `TXPMARESETDONE=0 / RXPMARESETDONE=0`. There is no reference clock on
the `MGTREFCLK0_126` pins that this IBERT was built against. The link test
cannot proceed until a live GTY refclk is identified. The XVC/DRP control path
is fully healthy: every DRP and PORT register was read on both dies.

**Evidence (MEASURED, `sio_pll.tcl` over `localhost:2542`, both dies identical):**

```
DEV xcvu35p_0
  PLL COMMON_X0Y2/QPLL0 STATUS=NOT LOCKED REFCLKLOST=1
  PLL COMMON_X0Y2/QPLL1 STATUS=NOT LOCKED REFCLKLOST=1
  GT MGT_X0Y8..11  TXPMARSTDONE=0 RXPMARSTDONE=0 TXPLL=QPLLCLK1 RXPLL=QPLLCLK1
DEV xcvu35p_1  (same)
```

`PORT.QPLL0REFCLKLOST=1` and `PORT.QPLL0FBCLKLOST=1` are the refclk input
buffer's own loss detectors: they assert when no toggling clock is present at
the MGTREFCLK pins. Both QPLLs, both dies. This is not a QPLL misconfiguration
(a wrong divider still locks with REFCLKLOST=0); it is an absent input clock.

**Two candidate causes, not yet separated:**
1. **Wrong refclk pin.** The carrier drives the bank-126 GTY refclk on a
   different MGTREFCLK input (0 vs 1, or a different bank), and this IBERT
   referenced the wrong one. Cheapest disambiguation: rebuild IBERT enumerating
   every quad/refclk and see which input's loss detector clears.
2. **Unprogrammed clock generator.** The carrier's transceiver refclk comes
   from an onboard programmable clock chip that the BMC / SD image must
   configure to output. If so, no pin choice locks until that chip is
   programmed, and the SD card (Section 7) likely carries that programming.

**Measured and REJECTED - do not retry:**
- Loading the FK33/`sqrl_arch` vendor `ibert.bit` to reveal the live refclk:
  that image targets the VU33P (FK33), not the VU35P; IDCODE mismatch, it will
  not configure these dies. Not a shortcut here.

**Not determined:** which of the two causes holds; whether any GTY refclk on
these modules is live at all; the carrier's clock-generator part and its
programming path.

**UPDATE 2026-09-27 (see Section 11):** the refclk sweep was run with the
census bitstream, not an IBERT rebuild. It RECONFIRMS this section's conclusion:
no valid GTY refclk is present on banks 124-128, and cause 2 (an unprogrammed
carrier clock generator) is now the favoured one. A first single read appeared
to show AD38 live; that was a floating-input noise trap, corrected below.

## 10. JTAG TCK max over CoE/XVC: not settable, transport-bound (MEASURED 2026-09-27)

**Question.** What is the maximum JTAG TCK the CoE/XVC path supports (the queued
capability probe)?

**Answer, up front.** TCK is NOT settable on this bridge. XVC `settck` is a
no-op: the bridge echoes the requested period verbatim for every value, from
1000 ns down to 1 ns (i.e. it will "agree" to 1 GHz), so the returned figure is
meaningless and there is no clamp to read a maximum from. The real limit is the
CoE transport (one Ethernet round-trip per XVC shift over the 100 Mbit LAN),
consistent with the empirical bitstream-load rate of ~0.7-1.4 MB/s. There is no
fast-TCK path to exploit for weight loading.

**Evidence (MEASURED, raw XVC client on the BC-250, `localhost:2542`):**

```
getinfo: -> xvcServer_v1.0:4096
settck req=   1ns -> actual=   1ns = 1000.000 MHz   <- echo, absurd
settck req=  10ns -> actual=  10ns =  100.000 MHz   <- echo
settck req= 100ns -> actual= 100ns =   10.000 MHz   <- echo
settck req=1000ns -> actual=1000ns =    1.000 MHz   <- echo
```

Every `settck` returns the request unchanged, so the bridge does not model a
JTAG clock at all; the value cannot be used as a capability.

**Measurement trap hit, and it bit the bridge:** the getinfo `4096` looks like a
4096-BYTE max shift vector, but an XVC `shift:` of 4096 bytes (32768 bits) hangs
the connection, and after an oversized shift the bridge's XVC listener thread
dies (port 2542 stops listening) while its telemetry loop keeps running. The
loaded IBERT bitstream is unaffected (config is not touched by a shift), and
restarting `sqrl_bridge ... skip 2542` restores XVC without reprogramming. Do
NOT push large XVC shifts at this bridge; keep per-transaction vectors small.

**Not determined:** the exact per-shift size ceiling before the XVC thread dies
(bracketed between a working small shift and 32768 bits; not pinned, because
each overrun requires a bridge restart and the answer does not change the
conclusion that throughput is round-trip-bound).

**Consequence for weights:** confirms Section 7 - the CoE/JTAG path is a
control/debug channel, not a weight-loading channel. Full-model weight loading
needs the module's own memory path (HBM/DDR via the carrier), not JTAG.

## 11. Refclk sweep via the census bitstream: only a 200 MHz LVDS sysclk is present (MEASURED 2026-09-27, ~19:30)

**Question.** Which of the module's GTY reference-clock inputs carries a live
clock (so IBERT can be rebuilt against a working refclk)?

**How (ruling).** Oren asked to "rebuild IBERT, sweep all refclks." I used the
already-built census bitstream (`hw/jc/census/`) instead of rebuilding IBERT.
The census buffers all ten MGTREFCLK inputs of banks 124-128 (IBUFDS_GTE4 ->
BUFG_GT) plus the three LVDS system clocks and counts each one's edges over a
CFGMCLK-timed window, read via VIO over XVC. It tests all ten refclk pins in one
load with no IBERT protocol constraints (IBERT's Custom protocol refused a
second custom quad, so a multi-quad IBERT sweep was not possible anyway). Cost
if wrong: the census only covers 124-128, not 129-131.

**Answer, up front.** No valid GTY reference clock is present on any MGTREFCLK
input of banks 124-128, on either die. The only clean clock on the modules is
the **200 MHz LVDS system clock (BC26)**, present and stable on both dies. This
reconfirms IBERT's `REFCLKLOST=1`. The transceiver refclk must be generated by
the carrier (cause 2 of Section 9); it is not currently running.

**Calibration (MEASURED).** CFGMCLK from the seq counter: dseq 116 over
20.033 s, 2^23 CFGMCLK cycles per seq -> **CFGMCLK = 48.57 MHz** (within the
STARTUPE3 50 MHz +-15% spec). Cross-check: BC26 counts 17.27M over the
2^22-cycle gate (0.0863 s) -> **200.0 MHz**, so the window model is right.

**Evidence (MEASURED, six samples per die, gate=0 clean reads):**

```
DIE 0 (xcvu35p_0):
  BC26 (sys) : 17.27M, 17.26M, 17.26M, 17.26M, 17.26M, 17.26M   spread 0.07%  STABLE = 200 MHz
  AD38 (126.0): 24.5M, 28.2M, 24.7M, 23.1M, 24.4M, 25.9M        spread +-10%  UNSTABLE = noise
  AC36 (126.1): 0 (all)                                          dead
  all other refclk (124/125/127/128): 0
DIE 1 (xcvu35p_1):
  BC26 (sys) : 17.13M (stable)                                   = 200 MHz
  AD38 (126.0): 0-2                                              dead
  AC36 (126.1): 0.10M, 0.21M, 1.87M, 0.19M, 0.19M, 0.21M         wild = noise
  all other refclk: 0
```

**Measurement trap hit (and corrected in-session).** A first SINGLE read showed
AD38 = 28.5M and I wrote "AD38 is LIVE," which appeared to contradict IBERT. It
was wrong. A clean clock reproduces (BC26 varied 0.07% across six reads); AD38
swung +-10% and die 1's AC36 swung 18x. A floating GTY differential input has
DIFF termination and picks up coupled noise, so its edge counter runs large but
unstable - it mimics a live clock in one read. The census RTL header says this
outright ("no oscillator behind it counts 0, or noise: read it twice"). The fix
was BC26 as a stability control: signal is stable, noise is not.

**Consequence for the link test.** No transceiver link is possible until the
carrier's GTY reference clock is enabled. A QPLL cannot take a refclk from a
fabric/LVDS clock, so the 200 MHz BC26 does not help the transceivers. Enabling
the GTY refclk is a carrier clock-generator / BMC / SD / ipcfg (`_sqrl-ipcfg`,
TCP 21347) matter - bench/RE work, Oren's domain (opens hardware config).

**Measured and REJECTED - do not retry:**
- Reading a GTY refclk edge-count ONCE and calling it live. AD38's single 28.5M
  read was floating-input noise. Always take several samples with a known-good
  clock (BC26) as the stability control.
- A multi-quad IBERT refclk sweep: the Custom_1/5Gbps protocol refuses a second
  custom quad ("Number of Lanes ... should not exceed 1"), and a quad's refclk
  source is only settable once its protocol is enabled. The census is the right
  instrument for this, not IBERT.

**Not determined:** whether banks 129-131 (outside the census's 124-128 window)
carry a refclk; the carrier's clock-generator part and how the BMC/SD enables
it; whether the 200 MHz BC26 count implies the sysclk oscillator is the only
populated clock source on the module.

## 12. Why the refclk is absent: no software path, no carrier clock source (read-only RE, 2026-09-27)

## 13. BMC ipcfg service RE: not reversible, and not a clock control (read-only, 2026-09-27)

**Question.** Can the BMC's `_sqrl-ipcfg` service (UDP 21347) enable the carrier
transceiver clock?

**Answer, up front.** No evidence it can, and it is not reverse-engineerable
from the available read-only artifacts. All signs are that it is the BMC's
IP-configuration service, orthogonal to clocking.

**Evidence (MEASURED, read-only):**
- `strings sqrl_bridge`/`sqrl_bridge_xvc`: NO reference to ipcfg, port 21347, or
  21363. The only network service either binary implements is the CoE JTAG link
  (it connects to the CoE port). Their "config" strings are all USB/libusb
  descriptor handling (`libusb_get_config_descriptor`, `bConfigurationValue`),
  the FK33-FTDI path, not the BMC. So no SQRL tool in the release speaks ipcfg.
- Direct mDNS multicast query (224.0.0.251:5353) for `_sqrl-ipcfg._udp`,
  `_sqrl-coe._tcp`, `_services._dns-sd._udp` and the BMC hostname: NO response.
  The BMC advertises on link-up events only, not on query, so its ipcfg TXT is
  not readable without a link bounce (which would drop the running census bridge
  and the BMC's DHCP lease).
- Read-only TCP connect scan of the BMC (198.51.100.58): the ONLY open TCP port
  is **21363 (CoE JTAG)**. 22/23/80/443/8080/2000/9100/502 all refused. 21347
  refused on TCP, confirming ipcfg is UDP-only. The BMC has no web/telnet/ssh
  admin interface.

**Conclusion.** The BMC exposes exactly two services: CoE JTAG (TCP 21363) and
ipcfg (UDP 21347, IP configuration). No client implements ipcfg, it is not
query-responsive, and blindly probing a UDP IP-config service risks changing the
BMC's address and dropping the link, so it is not a read-only-safe target. There
is no network-accessible BMC capability to enable a transceiver clock. If a
clock-enable path exists it lives in the BMC firmware (`jccfw 0.0.16`) on the SD
card, which needs physical access to read.

**Net for the interconnect:** the GTY reference-clock gap (Sections 9-12) has no
software or BMC-network fix. It is a hardware/firmware matter: read the SD image,
obtain the JCC2L schematic, or provide the Aurora refclk externally. Bench work,
Oren's domain.

## 14. Refclk sweep COMPLETE: banks 129-131 also dead, no GTY refclk anywhere (MEASURED 2026-09-27, ~19:30)

**Question.** Do banks 129-131 (outside Section 11's 124-128 window) carry a GTY
reference clock that could be routed to the link quad? This closes the "is there
a usable refclk anywhere / can an internal or other-bank clock feed the
transceivers" question.

**Answer.** No. A second census (`hw/jc/census/jc_census_hi.xdc`, the 10 refclk
slots remapped to banks 127-131, WNS +1.507, `census_hi.bit`) reads **exactly 0
on every MGTREFCLK input of banks 127, 128, 129, 130 and 131, on both dies, all
six samples**, while sysBC26 stays stable at ~17.2M (200 MHz) as the control.
Not even the floating-input noise that bank 126 showed - these inputs are quiet.

Combined with Section 11 (banks 124-128), the sweep now covers **all 8 bonded
GTY quads (banks 124-131, all 16 MGTREFCLK inputs)**: none carries a valid
reference clock. The only clean clock on either module is the onboard 200 MHz
LVDS sysclk (BC26).

**Consequence, final.** There is no internal or alternate-bank refclk to press
into service. An UltraScale+ GTY QPLL/CPLL reference must come from a dedicated
MGTREFCLK pin (no fabric-to-refclk path, and the LVDS sysclk is both wrong-pin
and too jittery), so the inter-module SERDES link is blocked until a clock is
physically provided on the MGTREFCLK pins - a carrier/BMC/rework matter. The
JCC2L "Lite" carrier drives no transceiver clock; SQRL's JCC2P-35 / JCC4P-35
carriers are the ones intended to, and worth checking before a custom carrier.

**Evidence:**

```
census_hi (banks 127-131), both dies, gate=0, all 6 samples:
  127.0 127.1 128.0 128.1 129.0 129.1 130.0 130.1 131.0 131.1 = 0 (every one)
  sysBC26 = 17.16-17.25M  (200 MHz, stable, control)
```

**Connector (photo 09, for the custom-carrier path):** the module-to-carrier
interface is a proprietary high-density open-pin-field mezzanine array (Samtec
SEARAY/SEAF-class, ~5-6 rows), NOT FMC (FMC is a 10-row 400/560-pin standard),
so off-the-shelf FMC carriers do not mate. Only SQRL's own Jungle Cat carriers
fit these JCM35P modules.

## 15. The refclk oscillators ARE on the carrier, UNPOPULATED: X1 and X2 (photos 2026-09-27)

**Finding.** With both modules removed (`images_from_oren/`), the carrier shows a
crystal/oscillator site below EACH module socket, designator **X1** and **X2**,
both **UNPOPULATED**. Each is a **QFN footprint with a central exposed thermal
pad and ~10-14 leads**, ringed by its own bias resistor (R4 for X1, R35 for X2)
and a cluster of decoupling caps (C12-C21 around X1; C92-C102 around X2), some of
which ARE populated. A small IC (U20/U21 near X1; U8 near X2) sits beside each -
likely a clock fanout/driver. The center pads are bare copper, no can fitted.
Closest shots: `IMG_8249.jpeg` (X1), `IMG_8253.jpeg` (X2), context in
`IMG_8242/8243`.

Every other clock on the board is accounted for and belongs to the BMC: the
STM32F765's own crystal (`080-A`) and the SMSC LAN8742 Ethernet PHY's crystal.
Neither touches the GTY.

**Interpretation.** This confirms the "same PCB as the high-speed JCC2P,
depopulated on the Ethernet-only Lite" model: the inter-module routing AND the
refclk oscillator footprints are already laid out; the Lite SKU simply omits the
oscillators (and the PCIe/USB parts, the other unpopulated fields). A center-pad
QFN with a bias resistor is an ACTIVE oscillator (XO/VCXO) or small clock IC, not
a 2-pin passive crystal. So enabling the GTY refclk is a **populate-one-part**
job at an existing footprint - not trace bodging. **This is the low-cost path to
the 2-module link.**

**Not yet determined:** the exact oscillator part (measure body + lead count, or
get the JCC2P BOM value for X1/X2); its frequency (likely the Aurora refclk,
156.25 MHz class); and which of X1/X2 feeds AD38 (`MGTREFCLK0_126`) vs the other
module/refclk. X1 and X2 sit under the module sockets, so they are accessible
only with the module removed.

**How to validate a populated oscillator (AD38 detector, staged on the BC-250):**
1. Populate/tack an oscillator at X1 (and/or X2) with the module off.
2. Reseat the module, power the carrier, reconnect to the BC-250 net.
3. `bash /home/labuser/sqrl_bridge_run/reload_ad38.sh` - programs the original
   census (banks 124-128, so AD38 = cnt(4)) and opens XVC.
4. `bash /home/labuser/read_ad38.sh` - samples every refclk of banks 124-128 six
   times and prints AD38's count. Nonzero AND stable across the six samples = a
   real refclk now present (a swinging count is floating noise, per Section 11).
   Whichever bank's count lights tells you which refclk that oscillator drives.
   `LED_C` on the board is also `cnt(4)>1000` = AD38-alive, if visible.

Passive alternative (board off, no FPGA): continuity-trace from X1/X2's output
pad to the module-connector pin, and check continuity between the two modules'
AD38 landings to learn whether the refclk is a shared net or per-module.
