# Qwen3.8-27B on Two FK33s: Plan

**Date:** 2026-09-23. **Status:** in progress; the area probe (Task 1) and the
base pack (Task 3) are running as this is written. Numbers below are labelled
MEASURED (a tool ran, named), DERIVED (arithmetic shown) or ESTIMATE.

**Goal:** run `Qwen3.8-27B-Q4_K_M.gguf` across the two FK33 cards as the
layer-split pipeline proven bit-exact on the 9B on 2026-09-23
(`hw/fk33/results/twocard_9b_2026-09-23/README.md`): card 0 holds blocks
0..K-1, card 1 holds K..63 plus the LM head, the host carries the residual.

**Prior work this depends on:** the two-card pipeline plan
(`2026-09-21-two-card-pipeline.md`, complete), the norm-gain counter root cause
(`docs/debugging/2026-09-23_the-norm-gain-is-indexed-by-a-per-token-counter.md`),
the per-token-counter and mmap traps in `CLAUDE.md`.

**Global constraints:** unchanged from the two-card plan. No hardware access
from any subagent. One Vivado per box; a card build runs on the workstation
alone under `MemoryHigh=24G MemoryMax=26G` with the swap guard; the BC-250 never
above `MemoryHigh=11G`. Build roots under `/mnt/storage/fk33_builds/<tag>/`.

## 1. What the 27B changes, and what it does not

| quantity | 9B | 27B | source |
|---|---|---|---|
| blocks (GDN + attention) | 32 (24 + 8) | 64 (48 + 16) | `rtl/model_cfg_pkg.vhd`, GGUF metadata |
| hidden | 4096 | 5120 | same |
| FFN | 12288 | 17408 | same |
| linear value heads (key heads) | 32 (16) | 48 (16) | same |
| attention q heads (kv heads, head dim) | 16 (4, 256) | 24 (4, 256) | same |
| region max `REGMAX` | 12288 | 17408 | MEASURED, GHDL probe of `region_max(mk_shape(...))` |
| seam `HADDR_W` | 14 | 15 | DERIVED, `clog2(REGMAX)` |
| norm-gain rows (2 per block + 1) | 65 x 4096 | 129 x 5120 | `hw/fk33/gen/norm_w_{9b,27b}.hex` |
| QK-norm vectors | 8 x 2 x 256 | 16 x 2 x 256 | `hw/fk33/gen/qkn_{9b,27b}.hex` |
| KV bytes per token (4 heads x 256, both caches) | 17408 | 17408 | manifest `kv_bytes_per_token`; unchanged |
| INT4 image, all blocks + head | 5.06 GB | 14.46 GB | MEASURED from `pack.log` sizes (GDN block 216,350,720 B, attention block 210,153,472 B, head 715,313,152 B) |

Datapath widths are identical (same `qwen35` architecture); only counts grow.
Subsystem A (the streaming matvec engine) does not change. B grows with value
heads (1.5x), C with query heads (1.5x), D with `REGMAX` and the norm table.

**The norm-gain ROM is the item that does not scale.** MEASURED in build 18's
synthesis log: `gen_vstub[0].gvr.gwl.wix_reg | 524288x11 | Block RAM`, i.e. the
gain image is stored as 11-bit codebook indices, 65 x 4096 = 266,240 live
entries. DERIVED: an 11-bit-wide ROM maps as 11 columns of 32K x 1 RAMB36, so
`ceil(266240 / 32768) x 11 = 99` tiles, which is what the top-level glue row
carries once its four buffers (8 tiles) are taken out. At 27B the image is
129 x 5120 = 660,480 entries: `ceil(660480 / 32768) x 11 = 231` tiles, **+132**.

DERIVED growth of the rest of D at 27B: `region_mem` scales with `REGMAX`
(100 -> ~142, +42), `swiglu_mem` with FFN (19.5 -> ~28, +8), the B state store
with value heads (28 -> 42 BRAM, 32 -> 48 URAM). Sum before B and C themselves:
567 + 132 + 42 + 8 + 14 = **763 of 672 block RAM tiles**. The 27B does not fit
this card with the norm gains in block RAM, whatever the probe says about B and
C. URAM cannot hold an initialised table on this device (recorded trap), so the
gains have to become a run-time store: written from HBM at model load, exactly
as the B constants already are (`docs/2026-09-18_b-constants-path.md`). That
is Task 2, and it is the same change that retires the per-token counter
indexing (the store can be indexed by block from the descriptor).

**C at 27B, MEASURED** (arm `attn27` of the BC-250 probe,
`sim/ooc_scorehdr.tcl` at the card's generics with `N_QH=24 LAYERS=16`,
post-`opt_design`, cap 11G reached so the wall time is throttled):

| | LUT | FF | BRAM | DSP |
|---|---|---|---|---|
| `attn_block` 27B OOC | 116,949 | 130,927 | 15.5 | 430 |
| of which `u_arr` | 76,535 | 58,871 | 0 | 384 |

The same-tree, same-script 9B control (`attn9`) is 86,827 LUT / 101,221 FF /
11 BRAM / 298 DSP, so the 27B delta is **+30,122 LUT (+34.7%), +29,706 FF,
+4.5 BRAM, +132 DSP**, all of it in `u_arr` (50,531 -> 76,535 LUT) and the
block's own plumbing (+2,005). DSP is exactly the structural `2 x G x KV_BLOCK`
(G = 6 query heads per KV head at 27B: 384 against 256). Full table in
`hw/fk33/results/probe27b_2026-09-23/README.md`.

**DSP** DERIVED: 2,087 + 128 (C) + about 70 (B at 1.5x) is about 2,285 of
2,880, which fits. **LUT** is the binding constraint after block RAM: build 18
is at 81.6% and C alone grows by 30,122 LUT (MEASURED, same-tree OOC delta;
the OOC harness over-counts the in-context 9B block by about 2,500, which
cancels in a delta). A 27B card needs levers: `FK33_C_KV_BLOCK=16` (MEASURED on the
9B: -14,383 LUT net and -112 DSP in `u_arr`, at the cost of KV granularity
and the score path's shape) is the first; the probe README will list the rest.

## 3. HBM budget per card: DERIVED, packer to confirm

From the packed sizes above, HBM 8,589,934,592 B per card, the 9B striped
card's top blocks (descriptor arena, gdn_const, host blocks: 7.0 MB) and a
27B GDN state of 39.7 MB per card (26.4 MB x 48/32 value heads; a card holds
24 GDN layers either way):

| split (card 0 blocks) | card 0 weights | card 0 KV tokens | card 1 weights (+head) | card 1 KV tokens |
|---|---|---|---|---|
| 0..31 | 6.874 GB | 95,912 | 7.589 GB | 54,821 |
| 0..32 | 7.090 GB | 83,484 | 7.373 GB | 67,250 |
| 0..33 | 7.306 GB | 71,056 | 7.156 GB | 79,678 |

So a 33/31 split leaves both cards above 65,536 tokens on a FLAT budget. The
striped layout is tighter: the 27 lanes are 15 on stack 0 and 12 on stack 1,
and the 9B allocator gives stack-0 lanes segments 1..15 only (segment 0 holds
the headers and `nonmatvec_f32.bin`, 2.8 MB). A card with 7.37 GB of weights
puts 15/27 of them, 4.09 GB, on stack 0 against 15 x 268.4 MB = 4.03 GB of
segment capacity: it does not fit unless the allocator may also use segment 0
above the common block (16 segments, 4.29 GB, 95% fill). Every split has one
card at or above 7.23 GB, so this is not avoidable by choosing K. Stack 1 then
carries 12/27 of the weights (3.28 GB), which its 12 own segments (3.22 GB)
cannot hold either, so the stack-1 lanes need a 13th segment (16 first, to
keep the KV arena contiguous at the top).

Both are now one opt-in flag, `pack_model_fk33.py --stripe-all-segments`
(commit 8e143c4), and its self-test MEASURED the budget on a synthetic 7.38 GB
half built from the real layout function and the real port map: without the
flag segment 1 overflows; with it but on the 12 own stack-1 segments,
segment 17 overflows; on 13 stack-1 segments (16..28) every stripe check
passes at 96.3% peak fill and **43,672 KV tokens** remain above the weights.
The flag off leaves the 9B layout byte-identical.

**CORRECTION, MEASURED by the packer 2026-09-23 12:40:** the per-card figures
above assumed a card reserves KV and GDN state for ITS layers only. It does
not: B and C index their arenas by the descriptor's GLOBAL layer ordinal, so a
card's arena spans the whole model (16 KV layers, 34,816 B per token; 48 GDN
layers, 78.7 MB), as the 9B cards' did. With that, the 33/31 split leaves
20,679 tokens on either card and **32,768 does not fit; the 27B cards are
built at `C_MAXPOS = C_CTXLEN = 16384`** (`FK33_C_MAXPOS=16384`,
`--card-maxpos 16384`). Both images are packed and agree on every base; see
the probe README's images section, which also costs the host-side base-offset
change that would recover 32k+ without RTL. The 32768 references below are
superseded.

Decisions following from this:
- **`C_MAXPOS = C_CTXLEN = 32768` for the 27B cards** (`FK33_C_MAXPOS=32768`,
  new trim in `gen_fk33_card.py`, coupled to `C_CTXLEN`; the packer takes the
  same number as `--card-maxpos 32768`). 65,536 does not fit beside 7.4 GB of
  striped weights.
- **The per-card 27B packs use `--stripe-all-segments`** (done, with teeth).
  The fallback if a real half still does not place is the LM head on the host
  (715 MB off card 1 and 15 A jobs off its program); a larger host change.

## Task 2: Norm gains as a run-time store, indexed by block

**DESIGN, 2026-09-23 (supersedes the URAM store sketched here earlier).** No
on-chip gain store at all. The only gain storage the norm needs is the NN x 16
bank already inside `rmsnorm_bf_mem`, and the loader that fills it is
per-op already. So the loader keeps its shape and changes its SOURCE and its
INDEX:

- **Index.** `const_base` on an `OP_VEC_NORM` becomes the norm ROW:
  `2*blk` for a block's first norm, `2*blk+1` for its FFN norm, `2*blocks`
  for the final norm. It is the field the oracle and `dprog_mutate` already
  call "the norm-weight selector", and both mutants on it (`m11`, `m04b`) are
  recorded as SILENT on the RTL today; that silence is this bug.
  `seq_vec_issue` latches it at `job_issue` beside `j_n` and exports `v_cb`.
  The per-token counter `nidx` is deleted, not kept as a fallback.
- **When.** The load starts at ACCEPT (`tk`), from the latched row, instead
  of prefetching "the next" row at the previous op's completion. It runs
  beside `S_RD` (both about NN cycles), so the serial cost is the fetch
  latency only.
- **Source, `NORM_HBM` false (sim, today's builds).** The existing
  `ixrom`/`cbrom` tables, indexed by the row. Fixes the split bug in every
  bench configuration with no area change.
- **Source, `NORM_HBM` true (card).** A read FSM on the `bst_*` channel:
  `(NN*2)/512` bursts of 16 beats x 32 B from
  `bst_const_base + NORM_OFF + row*NN*2`, `NORM_OFF =
  align4K(gdn_layers * gdn_const_bytes_per_layer)`, i.e. the norm rows are
  APPENDED to the GDN constants image the host already loads. Each 256-bit
  beat is 16 gain elements, written one per cycle. No ROM is elaborated, so
  the 99 (9B) / 231 (27B) block-RAM tiles go away.
- **Sharing `bst_*`.** A read-side mux inside `llama_top`: the norm fetch
  takes the channel only when the state store has no read outstanding and no
  `arvalid` up, and holds the store's `arready`/`rvalid` low while it owns
  it. The write side is untouched. The card's `bc_port_grant` already
  requests on `bst_arvalid` and counts outstanding bursts itself, so nothing
  outside `llama_top` changes. By dependency a norm and a B job never
  overlap; the mux makes that a property of the hardware, not of the program.
- **Row bursts never cross 4 KB**: base and `NORM_OFF` 4 KB aligned, row
  stride NN*2 a multiple of 512 at both shapes (8,192 / 10,240 B).

**Design, for the next card build:**
- [ ] A seam CTRL bit (e.g. bit 6 `CARD_RESET`) that holds a reset for N
      cycles on everything that can hold AXI state: `card/rst`, `bcgrant/rstn`,
      both `bc_cdc*` slave-side resets, and the engine's `core_aresetn`. NOT the
      seam itself (it must survive to report), not the XDMA or the HBM
      controller. OR'd with `core_reset` in the block design.
- [ ] The hazard to design against: resetting a master while its bursts are
      outstanding at the HBM leaves the clock converters' far side owing beats
      to nobody, which can hang the interconnect rather than free it. Options,
      to be decided with a bench: (a) quiesce first (block new AR/AW, wait for
      the grant's outstanding counters to drain, with a timeout), then reset;
      (b) also reset the converters' master side, which reaches into the
      `xdma/axi_aresetn` domain; (c) accept a PCIe hot reset as the only full
      reset and make the seam bit a "quiesce and reset the units" best effort.
- [ ] A CAPS_FLAGS bit for it, a `fk33ctl.py reset` verb, and the host
      (`run_prompt`, chat scripts) using it on a D watchdog instead of failing.
- [ ] A bench that wedges a unit (a slave that stops answering) and proves the
      reset returns the card to a state where the next token is correct.
- [ ] A `reset <addr>` verb in `/usr/local/sbin/fk33-pci` so the hot reset is
      sudoless like the reload (root install, Oren).
- [ ] Separately: root-cause the wedge itself. Capture `ERR_INFO` and the
      progress registers of BOTH cards on the first failure, before anything
