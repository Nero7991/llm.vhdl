# The token I/O path: the embedding gather, the LM head, and the argmax seam

**Date:** 2026-08-28. Branch `fpga`.
**Part:** `xcvu33p-fsvh2104-2L-e`, SQRL FK33. **Model:** Qwen3.5-9B, `MODEL = QWEN35_9B`
(`rtl/model_cfg_pkg.vhd:64-70`): `hidden = 4096`, `vocab = 248,320`.
**Answers:** worklog BACKLOG item 4.

**Labelling.** Every quantity is MEASURED (a named tool ran), DERIVED (arithmetic
shown here from MEASURED or normative inputs), or ESTIMATE (a judgement, with the
assumption stated). **No hardware was touched and no Vivado was run for this
document.**

---

## 0. The answers, up front

1. **The LM head really is 15 subsystem-A jobs, but the stride is 17,376, not
   `MAXROWS_BFP = 17,408`.** 17,408 is not a multiple of `ROWS_IF = 48`, and a
   row window can only begin on a tile boundary. `floor(17408/48)*48 = 17,376`,
   and `14 x 17,376 + 5,056 = 248,320` exactly. MEASURED: the 15 windows cover
   the rows with no gap and no overlap, cover the BYTES of all 27 sub-regions
   with no gap and no overlap, and all 15 are accepted by the re-statement of
   `matvec_int4_desc_axi`'s `S_CHECK`. Section 3.

2. **A row of a 6.5a-packed tensor is TWO contiguous 4 KB reads, not a
   27-master gather.** At `ROWS_IF = 48 / AXI_DW = 256` a beat is exactly two
   rows' 16-byte chunks, so row `rr` of a tile lives entirely inside weight
   sub-region `rr/2` and its scales entirely inside scale sub-region `rr/16`.
   DERIVED in section 2 and MEASURED by two independent decoders plus the BF16
   GGUF. This is the fact that makes the gather question worth costing at all.

3. **Recommendation: keep the gather on the host (spec D 3.2), and NOT because
   it is faster.** DERIVED in section 4: the marginal cost of host gather is
   6 to 35 us against a 38.27 ms token, i.e. **0.016% to 0.091%**, and an
   on-card gatherer costs 4 to 39 us of its own. The latency difference is
   inside both error bars. The decision is made by the **port budget** -- A
   takes 27 of 30 engine ports and B plus C already want 7 of the remaining 3
   (`docs/2026-08-27_hbm-residency-map.md` section 7) -- and by reversibility.

4. **Spec D 3.2's dequantize recipe is wrong by 2.6x and should be corrected.**
   Taken literally it does `floor((codebook[idx] * scale) >> 15)` and THEN
   BFP-packs, which throws away 15 fractional bits before the pack can place
   them. MEASURED against the BF16 GGUF over 48 rows: mean relative error
   **0.228 against 0.086**, worst **0.705 against 0.127**. Section 5. This is a
   host-software correction; no RTL changes.

5. **The lm_head job must be RAW mode, and then the 15-window argmax needs no
   exponent arithmetic and no index offset.** In RAW mode
   `y_exp = w_exp + x_exp - out_shift` with no per-job term
   (`rtl/matvec_core.vhd:959-961`), so all 15 windows report the same exponent.
   MEASURED on the real `rtl/sampler_stream.vhd` in GHDL: driving it with
   `clr` pulsed once per token and NOT between windows makes `token` come out as
   the **global** vocabulary id with no offset added anywhere. Section 6.

6. **Three contradictions found, and the RTL wins all three.** Section 7. The
   load-bearing one: `rtl/llama_top.vhd:737-741` states that `MAXROWS_BFP` "is
   checked only in BFP mode" and so "does not have to cover" the lm_head shard.
   That is true of `matvec_core.vhd:881` and **false of the descriptor front end
   the FK33 build uses**: `matvec_int4_desc_axi.vhd:683-688` rejects
   `n_rows > MAXROWS_BFP` in every mode, and must, because `sh_rows` is declared
   `integer range 0 to MAXROWS_BFP` (`:309`). The 15 windows are mandatory, not
   an optimisation.

## 1. Survey: where token I/O actually is today

### 1.1 The RTL is entirely stories260K

| unit | what it is | scale |
|---|---|---|
| `rtl/embed.vhd` | FSM over a file-init BRAM ROM, per-row `(mant, mult, shift)` reconstructed to a BFP row | `DIM = 64`, `VOCAB = 512` |
| `rtl/embed_rom_pkg.vhd` | `EMBED_MULT` / `EMBED_SHFT`, 512 entries each | generated by `tools/gen_embed_rom_pkg.py` from `mem/weights/embed*.mem` |
| `rtl/lm_head.vhd` | tied classifier, one shared 16x16 MAC over `VOCAB*DIM` | same ROM, `logit_valid`/`logit_v` streaming out |
| `rtl/lmhead_rom_pkg.vhd` | the same two tables again | `tools/gen_lmhead_rom_pkg.py` |
| `rtl/sampler_stream.vhd` | running int32 argmax, first-max-on-ties | `VOCAB` generic **declared and never referenced** |

At 9B those become `DIM = 4096`, `VOCAB = 248,320` and the embedding is
0.533 GiB, so the ROM approach does not scale by any factor: it is a different
design, not a bigger generic. `tools/gen_embed_rom_pkg.py` and
`tools/gen_lmhead_rom_pkg.py` read `mem/weights/embed*.mem`, which is the
stories260K dump, and have no path to a GGUF.

**The tie is gone at 9B.** `lm_head.vhd`'s header says the classifier reuses the
embedding ROM ("tied embedding: lm_head weight == token_embedding_table"). The
9B manifest carries `token_embd.weight` and `output.weight` as **two separate
tensors with different hashes** (`72fc532f...` and `619a7aa9...`), so nothing
about the 9B path may assume the tie.

### 1.2 What `llama_top` expects at the two boundaries

- **Embedding, in:** `rtl/llama_top.vhd:435-436` -- "The token embedding is
  written into R_X before `go`; the result is read back out of R_X after
  `tok_done`." The port is the host write path `hw_we / hw_reg / hw_addr /
  hw_data` into the region file. **`llama_top` does not contain an embedding
  unit and does not want one.** Its contract is already spec D 3.2's.
- **LM head, out:** `rtl/llama_top.vhd:133-134` -- "There is no sampler and no
  lm_head output. The final A job is issued with `dst = R_NONE` and its result
  is discarded." So the output boundary is **absent**, not placeholder.

That asymmetry is the honest survey answer: the input boundary is specified and
unimplemented on the host side; the output boundary is not wired at all.

### 1.3 Both tensors are already packed, resident and hashed

`/mnt/storage/llama-models/qwen35-9b-mv4i/manifest.json`, MEASURED by reading it:

| tensor | M x K | `w_exp` | `out_shift` | bytes | `hbm_offset` |
|---|---|---|---|---|---|
| `output.weight` | 248,320 x 4,096 | 8 | 3 | 572,207,104 | 0 |
| `token_embd.weight` | 248,320 x 4,096 | 8 | 3 | 572,207,104 | 572,207,104 |

Geometry `rows_if=48, axi_dw=256, block=32, nports_w=24, n_scale_sub=3`.
Both are ordinary `.mv4i` files: **the embedding is INT4, not BF16.** Every
"8 KB at bf16" cost model has to be re-derived from that, and section 4 does.

## 2. What an embedding lookup actually has to do

### 2.1 The addressing, DERIVED

From `tools/pack_int4.py:455-467` and spec 6.5a:

- the tile word for (tile `t`, block `b`) is `ROWS_IF*BLOCK*4 = 6,144` bits,
  with row `r` of the tile at bits `(r+1)*128-1 downto r*128`, row 0 at the LSB;
- weight sub-region `p` is bytes `[p*32, (p+1)*32)` of that word at
  `AXI_DW = 256`;
- **32 bytes is exactly two rows' 16-byte chunks.**

Therefore row `rr` of a tile is entirely inside weight sub-region `rr // 2`, in
the low or high 16 bytes of a beat by `rr & 1`. Beats run tile-major then block,
so the whole row's nibbles for all `NB = 128` blocks are 128 **consecutive**
beats: one contiguous 4,096-byte read, of which 2,048 bytes are this row.

Scales are the same shape one level up. A superword is
`n_scale_sub * AXI_DW = 768` bits = 48 uint16 = one scale per row of the tile,
and scale sub-region `q` is bytes `[q*32, (q+1)*32)` of it, i.e. rows
`16q .. 16q+15`. So row `rr`'s scales are uint16 index `rr % 16` of 128
consecutive beats in scale sub-region `rr // 16`: a second contiguous 4,096-byte
read.

**Per token: two contiguous 4 KB reads, 8,192 bytes, both 4 KB-aligned.**
MEASURED for token 12,345 of `token_embd.weight`:

```
addressing    tile=257 row_in_tile=9 w_sub=4 half=1 s_sub=0 s_idx=9
weight read   0x51DA000 .. 0x51DB000 (4096 bytes, contiguous)
scale read    0x1E612000 .. 0x1E613000 (4096 bytes, contiguous)
```

This is the fact that changes the on-card option from "a scatter engine" to "an
AXI master that issues two bursts", and it is why the option is costed rather
than dismissed.

### 2.2 The arithmetic

`w = floor((codebook[idx] * scale) >> 15)` represents `W * 2^w_exp`
(`tools/pack_int4.py:331` sets the quantization target to `W * 2^w_exp`, and
`:344` reconstructs as `cb[ix] * scale/32768`). The row is then BFP-encoded to
`int16 + one exponent` under this repository's `value[j] = mant[j] * 2^(-x_exp)`
convention, with `sh = msb_pos(amax) - 14` **not clamped at 0**, because a left
shift is what `rtl/embed.vhd` already does (its `S_EXP_IT` searches `e` downward
from 30 and accepts `net >= 0`, an exact left shift).

Section 5 shows that *where* the `>> 15` goes is worth 2.6x of accuracy.

## 3. The LM head: 15 windows, and the arithmetic that says 15

### 3.1 Why one job is impossible

`rtl/matvec_int4_desc_axi.vhd:683-688` refuses a descriptor whose `n_rows`
exceeds `MAXROWS_BFP`, which the FK33 build sets to 17,408 (`:108`). The refusal
is unconditional in `out_mode` and is structurally required: `sh_rows` is
`integer range 0 to MAXROWS_BFP` (`:309`), so a larger value is a bound
violation, not merely an unchecked one.

### 3.2 Why the stride is 17,376 and not 17,408

A window that does not start at row 0 is expressed by advancing all 27 bases by
whole tiles (`tools/gen_mv4i_desc.py::build_descriptor`), because a sub-region's
beats run tile-major. So `row_start` must be a multiple of `ROWS_IF = 48`.

```
MAXROWS_BFP mod ROWS_IF = 17408 mod 48 = 32          NOT a tile multiple
STRIDE = floor(17408 / 48) * 48 = 362 * 48 = 17376
jobs   = ceil(248320 / 17376) = 15
cover  = 14 x 17376 + 5056 = 248320                  exact
```

DERIVED, and MEASURED by `tools/gen_lmhead_windows.py`:

| job | `row_start` | `n_rows` | `tiles` | `w_beats` | `s_beats` | `w_base[0]` |
|---|---|---|---|---|---|---|
| 0 | 0 | 17,376 | 362 | 46,336 | 46,336 | `0x1000` |
| 1 | 17,376 | 17,376 | 362 | 46,336 | 46,336 | `0x16B000` |
| ... | | | | | | |
| 13 | 225,888 | 17,376 | 362 | 46,336 | 46,336 | `0x1263000` |
| 14 | 243,264 | 5,056 | 106 | 13,568 | 13,568 | `0x13CD000` |

```
PASS row cover
PASS byte cover
PASS gateware acceptance
PASS y_exp invariance
WINDOW SET PASS
```

The byte cover is the check that matters: `14 x 46,336 + 13,568 = 662,272` beats
x 32 B = **21,192,704 B**, which is exactly `sub_bytes()` for the whole tensor,
and every one of the 27 sub-regions abuts window to window with no slack. A row
cover can be exactly right while the bases are wrong -- that is worklog OI-1
case 19, the defect the gateware cannot see -- so the two are computed from
different descriptor fields and checked separately.

The same set is emitted and passes for `token_embd.weight`, whose only
difference is `hbm_base = 0x221B3000`.

### 3.3 A corner that closes itself

`matvec_core`'s `ybuf` is `array(0 to TILES-1)` with
`TILES = ceil(MAXROWS_BFP / ROWS_IF) = 363` (`rtl/matvec_core.vhd:120,202`), and
worklog OI-8 is an index one past the end whenever a job's `tiles` reaches
TILES. **A tile-aligned window can never reach it**: flooring `MAXROWS_BFP` to a
tile boundary is precisely what removes the last tile, so `STRIDE/ROWS_IF = 362`
by construction. Recorded because it is a coincidence worth not relying on
silently. (OI-8 is separately fixed in the working tree by `ybuf_addr`,
`rtl/matvec_core.vhd:128-130`.)

### 3.4 The mutation table

MEASURED, `tools/gen_lmhead_windows.py --mutate`:

| mutant | verdict | what fired |
|---|---|---|
| m0 clean (control) | PASS | must PASS or the table means nothing |
| m1 stride = `MAXROWS_BFP` (17,408) | KILLED | `build_descriptor` refuses: row_start 17,408 is not a multiple of 48 |
| m2 stride rounded UP to 363 tiles | KILLED | gateware acceptance, 14 windows |
| m3 count from `MAXROWS_BFP`, stride from tiles | KILLED | window 14 would run past `M` |
| m4 last window dropped | KILLED | row cover (1), byte cover (27) |
| m5 two windows' weight bases swapped | KILLED | **byte cover only** |
| m6 `out_mode` BFP instead of RAW | KILLED | `y_exp` invariance |

6 of 6. **m5 is the one that justifies the byte check**: the row cover is
completely silent on it, because the rows are still exactly right.

## 4. Host gather or on-card gather: the arithmetic

### 4.1 The token budget the comparison is against

The published `30.49 ms / 32.80 tok/s` at `ROWS_IF = 48`
(`docs/2026-08-28_can-27-read-masters-be-served.md:292`) assumes
`f_core = 237.8 MHz` and `ACLK = 300 MHz`. Both are withdrawn by that document's
own appended correction, which MEASURED, by out-of-context synthesis of
subsystem A at the FK33 geometry, `ACLK = 189.50 MHz` and `f_core = 221.83 MHz`.
DERIVED from those:

```
supply = 27 x 32 B x 189.50e6 = 163.7 GB/s
demand = 27 x 32 B x 221.83e6 = 191.7 GB/s
duty   = 191.7 / 163.7        = 1.1708          the array is starved

array-limited at 221.83 MHz   = 30.49 ms x 237.8 / 221.83 = 32.685 ms
feed-limited                  = 32.685 x 1.1708           = 38.27 ms
                                                          = 26.13 tok/s
```

**Every number below is against 38.27 ms, not 30.49 ms.**

### 4.2 Host gather (spec D 3.2)

The host is already in the per-token loop by construction: it reads the argmax
triple back, chooses the next token, and pulses `go` (D 3.2; B 1.2; C 1.2). So
the PCIe round trip exists whether or not the embedding rides on it, and only
steps 2 and 3 below are marginal.

| step | cost | label |
|---|---|---|
| 1. read the argmax triple (BAR read, non-posted) | 1-2 us | ESTIMATE, and **not marginal** |
| 2. dequantize + BFP-pack one 4,096-element row | 1-10 us | ESTIMATE: ~16k integer ops, scalar C at ~3 GHz, sub-us vectorised |
| 3. H2C DMA of 8,192 B into region X | 5-25 us | ESTIMATE, see below |
| 4. `x_exp` write + `go` (posted) | <1 us | ESTIMATE |

**Marginal cost of the gather = steps 2 + 3 = 6 to 35 us**, i.e. **0.016% to
0.091%** of the 38.27 ms token. Even at a deliberately absurd 100 us it is
0.26%, and 26.13 tok/s becomes 26.06.

On step 3, an honest statement of what is and is not known: the MEASURED H2C
rate is **3.27 GB/s (1,024 MB in 0.328 s)**
(`docs/debugging/2026-08-28_fk33-first-light.md:141`), which puts 8,192 B at
2.5 us of wire time. **No small-transfer latency has ever been measured on this
card.** The 0.64-0.66 GB/s seen on 19-29 MB tensor loads is not usable here: it
is hash-bound, not DMA-bound
(`docs/debugging/2026-08-28_fk33-9b-full-weight-pack.md:270-284`). The 5-25 us
band is XDMA descriptor-setup-plus-completion judgement, and it is the single
softest number in this document.

**The host also needs the packed table in its own RAM**, 572,207,104 bytes,
either mmapped from the `.mv4i` or resident. That is free on a 32 GB host.

### 4.3 On-card gather

| step | cost | label |
|---|---|---|
| two 4 KB bursts, 256 beats total, at `ACLK = 189.50 MHz` | 1.35 us | DERIVED |
| HBM first-word latency, twice | ~0.5 us | ESTIMATE; **never measured** (residency map section 8 item 1) |
| dequantize + amax pass + requantize pass, 8,192 element-cycles at 221.83 MHz | 36.9 us at 1 lane, 4.6 us at 8 lanes, 2.3 us at 16 lanes | DERIVED |

**Total 4 to 39 us.** The same order as the host round trip, and worse than it
unless the datapath is parallelised 8 ways.

### 4.4 The recommendation, and what it costs

**Recommend host gather.** In order:

1. **The latency saving is not real.** 6-35 us against 4-39 us, both against
   38.27 ms. The bands overlap. Anyone choosing on-card gather for speed is
   choosing on noise.
2. **The port budget decides it.** A takes 27 of 30 engine ports at
   `ROWS_IF = 48`; B wants 4 masters and C wants 2 reads plus 1 write, and 3
   remain (residency map section 7, which calls this "a real conflict" in its
   own words). A 28th master for a 0.09% latency saving is the wrong trade.
3. **The host is already in the loop.** The round trip is sunk cost.
4. **It is reversible at zero cost to the token stream**, provided the recipe is
   shared. `tools/embed_gather.py` is that shared recipe: an on-card unit
   implementing its `direct` decoder and its `bfp_pack` produces identical
   tokens, so the decision can be revisited after first light without
   re-establishing bit-exactness.

**What it costs, stated rather than buried:**

- **tok/s becomes sensitive to host jitter.** A 1 ms scheduling hiccup is 2.6%
  of a token; 10 ms is 26%. On-card gather would make the token time depend on
  nothing outside the card. This is the one genuine argument for the other side
  and it is not a latency argument.
- **`token_embd.weight.mv4i` becomes 572,207,104 bytes of HBM that nothing
  reads** -- 6.66% of the 8 GiB, loaded and hash-verified for nothing. At the
  manifest's own `kv_bytes_per_token = 65,536` that is **8,731 tokens of
  context**. **This is a decision for Oren, not an implementation:** drop it
  from the load set and recover the space, or keep it as pre-positioning for a
  future on-card gatherer. Nothing in this track should choose.

## 5. Spec D 3.2's recipe is 2.6x worse than it needs to be

D 3.2 (`docs/superpowers/specs/2026-08-24-transformer-sequencer-design.md:354-361`)
makes the host recipe normative: "dequantize the INT4 row with the same integer
arithmetic as A 7.4 (`codebook[idx] * scale`, floor `>> 15` per block -- exact
integers throughout), then BFP-pack the values to int16 + one exponent".

Read literally that shifts right by 15 first, so the row lands in `[-127, 127]`
and the subsequent BFP pack has nothing left to place. MEASURED for token 12,345:
the amax of the shifted row is **7**, i.e. three bits of magnitude survive out of
a nominal four bits per weight.

MEASURED, `tools/embed_gather.py --compare`, 48 rows against the BF16 GGUF:

| recipe | mean relative error | worst |
|---|---|---|
| `d32` -- `>> 15` before the pack (spec D 3.2 as written) | **0.22794** | 0.70541 |
| `wide` -- `>> 15` folded into the pack's own shift | **0.08630** | 0.12667 |

**2.641x on the mean.** The `wide` figure, 0.086, is the intrinsic loss of a
4.5-bit pack and is the floor; `d32` adds a second quantization on top of it for
nothing.

It shows up a second time, and more alarmingly, in the oracle's own resolution.
MEASURED, `--separation`, decoding row `t` and comparing it against the GGUF row
`t` (matched) and row `t+1` (mismatched), 199 pairs each:

| recipe | matched relerr | mismatched relerr | gap |
|---|---|---|---|
| `wide` | 0.0741 .. 0.1267 | 0.7116 .. 5.3071 | **5.6x, cleanly separable** |
| `d32` | 0.1570 .. 0.7054 | 0.7306 .. 5.3614 | **3.6%, NOT separable** |

Under the spec-as-written recipe a decoded embedding row is barely
distinguishable from its **neighbour**. That is a statement about the recipe,
not about the oracle.

**Recommended correction to D 3.2:** keep `codebook[idx] * scale` as the
integer product, do not shift it, and let the BFP pack's own
`sh = msb_pos(amax) - 14` place it, with `sh` allowed to be negative. The
value carried is then `mant * 2^-(w_exp + 15 - sh)`. This is exactly what
`rtl/embed.vhd` already does on the stories260K path, so it is a return to the
existing convention rather than a new one. `tools/embed_gather.py --recipe wide`
is the reference and is the default.

**Not determined:** what either recipe costs in perplexity. Relative error on a
weight row is not perplexity, and this document does not claim it is.

## 6. The argmax and sampling boundary

### 6.1 RAW mode is forced, and by a reason spec D 3.3 does not give

`rtl/matvec_core.vhd:959-961`:

```
y_exp <= (w_exp + x_exp)                   when out_mode = "10"   -- PARTIAL
         (w_exp + x_exp - os_r - ns_r)     when out_mode = "00"   -- BFP
         (w_exp + x_exp - os_r);                                  -- RAW
```

`ns_r` is the **per-job** normalisation shift, derived from that job's own amax
scan. Across 15 windows it differs, so in BFP mode the 15 streams are on 15
different scales and a running max over them is meaningless without exponent
arithmetic. In RAW mode there is no per-job term, and `w_exp`, `out_shift` come
from the same `.mv4i` header while `x_exp` is the same activation, so **all 15
windows report an identical `y_exp` and the comparison is a plain signed int32
compare**. Spec D 3.3 picks raw mode; this is why it had to.

`tools/gen_lmhead_windows.py` checks this as `y_exp invariance` and mutant m6
(BFP instead of RAW) is killed by it.

### 6.2 The 15 windows share one running argmax, with no offset arithmetic

`rtl/sampler_stream.vhd` keeps `idx` as a plain unconstrained `integer` that
advances on every `in_valid` and is reset only by `rst` or `clr`. So if `clr` is
pulsed **once per token, before window 0, and never between windows**, `idx`
runs 0 .. 248,319 across the whole set and `best_i` is the global vocabulary id
**directly**. No `row_start` is added anywhere.

Two conditions, and both are load-bearing:

- **`clr` must not be pulsed at a window break.** D's per-job teardown must not
  reach the sampler.
- **The windows must be issued in ascending `row_start` order.** The index is a
  count, not an address.

MEASURED on the real `rtl/sampler_stream.vhd` under GHDL 1.0.0, 8 cases with the
global maximum placed in the first window, the last window, the short tail, at
each window boundary, and a tie case (first max must win):

```
clean:  ORDER ascending, clr once per token      tb_sw2: PASS (8 cases)
m1:     clr pulsed at each window break          tb_sw2: FAIL 8
m2:     windows issued descending                tb_sw2: FAIL 8
```

Both mutations kill all 8 cases, so the check has teeth on both conditions.

**Not made a gate row, deliberately.** `sim/regress.sh` is shared with three
running tracks and `BASELINE_PASS` moved twice today (78 then 80); adding a row
for a bench that duplicates no existing coverage but does add a vector file was
judged the wrong risk tonight. The bench is small and is reproduced verbatim in
section 9 so it can be added by whoever next owns `sim/`.

### 6.3 One incidental defect

`sampler_stream`'s `VOCAB` generic is **declared and never referenced** in the
architecture. Nothing bounds `idx`, which is why the multi-window use works at
all. Harmless today; recorded because a future reader will assume the generic
does something.

## 7. Contradictions found, and which side wins

**Where a document and the RTL disagree, the RTL wins** (CLAUDE.md).

### 7.1 `llama_top` on `MAXROWS_BFP`: the RTL disagrees with itself

`rtl/llama_top.vhd:737-741`:

> "The lm_head step's `n_rows` is the vocabulary shard, which is far larger than
> any region -- it is issued with `dst = R_NONE` and in raw mode, so
> `MAXROWS_BFP` (checked only in BFP mode) does not have to cover it."

That is a correct reading of `rtl/matvec_core.vhd:881`, which gates the check on
`out_mode = "00"`. It is **false of the descriptor front end the FK33 build
uses**: `rtl/matvec_int4_desc_axi.vhd:683-688` checks
`unsigned(lo32(dw(1))) > MAXROWS_BFP` unconditionally, and cannot do otherwise,
because `sh_rows` is declared `integer range 0 to MAXROWS_BFP` (`:309`).

So a single 248,320-row lm_head job is refused with `EC_DESC` before anything
runs, and the 15 windows are mandatory. `llama_top`'s comment predates the
descriptor control plane (`a4f7e17`) and is now stale rather than wrong at the
time. **Not fixed here: `rtl/llama_top.vhd` is not this track's file.**

### 7.2 The manifest does not implement the residency map

`docs/2026-08-27_hbm-residency-map.md` section 3 places 27 lane arenas of
160 MiB, one per pseudo-channel, and derives `max_context = 198,415` from
`kv_bytes_per_token = 17,408`. The manifest that was actually packed and loaded
uses a **flat contiguous layout** (`hbm_offset` runs 0 .. 5,056,995,328 with no
arena stride) and reports `kv_bytes_per_token = 65,536`,
`max_context_tokens = 52,756`.

Both may be defensible; they are not the same design, and the manifest is the
one whose bytes are on the card. Recorded, not adjudicated -- neither file is
this track's.

### 7.3 One tensor straddles the HBM stack boundary

MEASURED by walking the manifest: **`blk.7.ffn_gate.weight` spans

**Not this track's file** (`tools/pack_model_fk33.py` and the manifest belong to
the packer). Raised so it is not discovered by a wrong answer.

## 8. What was built, and what it was checked against

### 8.1 `tools/embed_gather.py`

The gather recipe plus its oracle. Three decoders, and the third is the reason
this is not a round trip:

- **`direct`** -- the addressing of section 2.1. What a driver or a fabric unit
  implements.
- **`reassemble`** -- rebuild the whole tile word from all 24 weight sub-regions
  and the whole superword from all 3 scale sub-regions, then read the row out.
  Shares no addressing arithmetic with `direct`.
- **`gguf`** -- the BF16 row straight out of
  `Qwen3.5-9B-BF16.gguf`, never touching the packed file.

`direct` vs `reassemble` alone would be a two-decoder agreement and would pass
for two decoders wrong the same way. The GGUF cannot be bit-exact (the pack is
lossy), so it is gated on a relative-error and correlation band whose two
populations were **measured** rather than chosen (section 5).

MEASURED, `--selftest --n 1000`, `token_embd.weight`, recipe `wide`:

```
tokens checked          1000
direct vs reassemble    0 mismatches
bfp pack disagreement   0
checked against GGUF    1000 (0 all-zero rows skipped)
worst relative error    0.12667
worst correlation       0.99200
rows the GGUF rejects   0
SELFTEST PASS
```

and `--selftest --n 64` on `output.weight` (the untied classifier) likewise
PASSes, worst relerr 0.11286.

The token set is not purely random: `sample_tokens()` forces row 0, row `M-1`,
the rows either side of every tile / beat-half / scale-sub-region boundary, and
the first row of the **partial** last tile, then fills with a seeded random
spread. Random sampling reaches none of those reliably.

**Mutation table**, MEASURED, `--mutate --n 64`:

| mutant | verdict | what fired |
|---|---|---|
| m0 clean (control) | PASS | -- |
| m1 nibble order swapped | KILLED | **gguf only**, 64/64, worst relerr 1.447, corr -0.055 |
| m2 wrong half of the beat | KILLED | decoder disagreement 64/64 |
| m3 weight sub-region + 1 | KILLED | decoder disagreement 57/64 |
| m4 tile + 1 | KILLED | decoder disagreement 61/64 |
| m5 scale sub-region + 1 | KILLED | decoder disagreement 42/64 |
| m6 scale index within beat + 1 | KILLED | decoder disagreement 64/64 |
| m7 beats read block-major not tile-major | KILLED | decoder disagreement 64/64 |
| m8 codebook reversed | KILLED | **gguf only**, 64/64, worst relerr 2.051, corr -0.996 |
| **m9 BFP headroom `TARGET_MSB` 14 -> 13** | **SILENT** | **nothing** |
| **m10 BFP pack truncates instead of rounding** | **SILENT** | **nothing** |

8 of 10. The two silent rows are the honest resolution floor and are the most
useful lines here:

- **m9 and m10 are invisible to every check in this file.** Both decoders share
  `bfp_pack`, so the agreement check cannot see them by construction, and the
  GGUF oracle is far too coarse: a one-bit headroom change or a half-LSB
  rounding change is orders of magnitude below the 0.086 intrinsic pack error.
  **Closing them needs a bit-exact oracle at the BFP-pack level**, which means
  either a C reference for this pack or the RTL itself. Neither exists.
- **m1 and m8 are killed by the GGUF and by nothing else.** They are the direct
  evidence that the external oracle earns its cost: a nibble-order error and a
  reversed codebook are exactly the m7-class defects that two self-consistent
  decoders agree about.
- m3, m4 and m5 kill on 57, 61 and 42 of 64 rather than all 64, because the
  mutations clamp at a boundary and become no-ops for rows already at the top
  sub-region, the last tile, or the last scale sub-region. That is a property of
  the mutants, not of the checks.

## 9. The sampler window bench, for whoever adds it to the gate

Kept in full because it was deliberately not committed as a `sim/tb_*.vhd` gate
row (section 6.2). The generics ARE the mutation switches, which is the point: a
mutation you have to edit the file to run is a mutation nobody re-runs.

```
ghdl -a --std=08 rtl/sampler_stream.vhd tb_sw2.vhd
ghdl -r --std=08 tb_sw2 -gVEC=vec.txt -gORDER=0 -gCLRBRK=0   -- PASS (8 cases)
ghdl -r --std=08 tb_sw2 -gVEC=vec.txt -gORDER=0 -gCLRBRK=1   -- FAIL 8, m1
ghdl -r --std=08 tb_sw2 -gVEC=vec.txt -gORDER=1 -gCLRBRK=0   -- FAIL 8, m2
```

### 9.1 The vector generator

The oracle is Python's own `max`/`index`, which is first-max-on-ties and
therefore the same tie rule `sampler_stream` implements. It is an oracle rather
than a round trip because it never models the windowing at all: it takes the
argmax of the flat stream, and the bench is what splits that stream into
windows.

```python
import random
random.seed(20260828)
CASES = []
def mk(nwin, stride, tail, maxpos):
    n = (nwin - 1) * stride + tail
    v = [random.randint(-2**30, 2**30) for _ in range(n)]
    v[maxpos] = 2**30 + 12345          # a unique global max
    return v, [stride] * (nwin - 1) + [tail]
# the max placed in the first window, mid-window, either side of both window
# boundaries, and in the short tail
for maxpos in (0, 5, 199, 200, 201, 399, 437):
    CASES.append(mk(3, 200, 38, maxpos))
v, w = mk(3, 200, 38, 0)
v[0] = 2**30 + 999; v[300] = 2**30 + 999      # tie: the FIRST must win
CASES.append((v, w))
with open("vec.txt", "w") as f:
    f.write("%d\n" % len(CASES))
    for v, w in CASES:
        f.write("%d %d %d\n" % (len(v), len(w), v.index(max(v))))
        f.write(" ".join(str(x) for x in w) + "\n")
        for x in v:
            f.write("%d\n" % x)
```

### 9.2 `tb_sw2.vhd`

```vhdl
-- scratch bench v2: the same claim, but with the whole stream buffered so the
-- WINDOW ORDER can be permuted.  ORDER=0 issues windows ascending (the claim);
-- ORDER=1 issues them descending, which is the scheduling defect that makes
-- the running index stop being the vocabulary id.
library ieee;
use ieee.std_logic_1164.all;
use ieee.numeric_std.all;
use std.textio.all;

entity tb_sw2 is
  generic( VEC : string := "vec.txt"; ORDER : integer := 0; CLRBRK : integer := 0 );
end entity;

architecture sim of tb_sw2 is
  signal clk, rst, clr, iv : std_logic := '0';
  signal ivv  : std_logic_vector(31 downto 0) := (others => '0');
  signal tokn : integer;
  signal stop : boolean := false;
begin
  clk <= not clk after 5 ns when not stop else '0';

  dut: entity work.sampler_stream
    generic map( VOCAB => 512 )
    port map( clk => clk, rst => rst, clr => clr,
              in_valid => iv, in_v => ivv, token => tokn );

  drive: process
    file f : text open read_mode is VEC;
    variable l : line;
    variable ncase, n, nwin, expect, x, w : integer;
    variable fails : integer := 0;
    variable wl    : integer_vector(0 to 63);
    variable st    : integer_vector(0 to 63);
    variable vals  : integer_vector(0 to 4095);
    variable wi    : integer;
  begin
    rst <= '1'; wait until rising_edge(clk); wait until rising_edge(clk);
    rst <= '0'; wait until rising_edge(clk);

    readline(f, l); read(l, ncase);
    for c in 0 to ncase-1 loop
      readline(f, l); read(l, n); read(l, nwin); read(l, expect);
      readline(f, l);
      for i in 0 to nwin-1 loop read(l, w); wl(i) := w; end loop;
      st(0) := 0;
      for i in 1 to nwin-1 loop st(i) := st(i-1) + wl(i-1); end loop;
      for j in 0 to n-1 loop readline(f, l); read(l, x); vals(j) := x; end loop;

      clr <= '1'; wait until rising_edge(clk); clr <= '0';
      for i in 0 to nwin-1 loop
        if ORDER = 0 then wi := i; else wi := nwin-1-i; end if;
        for j in 0 to wl(wi)-1 loop
          ivv <= std_logic_vector(to_signed(vals(st(wi)+j), 32));
          iv  <= '1';
          wait until rising_edge(clk);
        end loop;
        iv <= '0';
        if CLRBRK = 1 then
          clr <= '1'; wait until rising_edge(clk); clr <= '0';
        end if;
        for k in 0 to 3 loop wait until rising_edge(clk); end loop;
      end loop;
      wait until rising_edge(clk);
      if tokn /= expect then
        report "case " & integer'image(c) & ": token " & integer'image(tokn)
             & " expected " & integer'image(expect) severity error;
        fails := fails + 1;
      end if;
    end loop;

    if fails = 0 then
      report "tb_sw2: PASS (" & integer'image(ncase) & " cases)" severity note;
    else
      report "tb_sw2: FAIL " & integer'image(fails) severity error;
    end if;
    stop <= true;
    wait;
  end process;
end architecture;
```

## 10. What was NOT verified

Stated as an explicit list, because a tidy conclusion that overstates is worth
less than an honest gap.

1. **Nothing was run on hardware.** No `xsdb`, no `hw_server`, no bitstream, no
   `/dev/xdma*`. Every PCIe latency figure in section 4 is ESTIMATE.
2. **The 15 descriptors were never executed by the RTL.** They pass
   `rtl_would_reject`, which is a *re-statement* of `S_CHECK` in
   `tools/gen_mv4i_desc.py`, not the entity itself.
   `sim/tb_mv4i_desc_image.vhd` is the judge and was not run against this set.
   A disagreement between the prediction and the RTL would itself be a finding
   and has not been looked for here.
3. **No lm_head result was ever computed.** The window set is proved to tile the
   tensor; nothing here shows that 15 jobs produce the same 248,320 logits as
   one hypothetical job would. That needs `ref/matvec_int4.c` run 15 times
   against a whole-tensor run, and it is the obvious next check.
4. **The BFP pack has no bit-exact oracle** (mutants m9, m10). Its rounding and
   headroom are unverified against anything.
5. **Perplexity was not measured**, for either recipe. Section 5's 2.6x is a
   relative-error ratio on weight rows and nothing more.
6. **HBM read latency is still unmeasured** (residency map section 8 item 1), so
   the on-card gather figure in 4.3 carries an unmeasured term.
7. **Prefill was not costed.** Everything in section 4 is per decode token. If
   prefill is teacher-forced one position at a time (B 1.2, C 1.2) the same
   per-token cost applies and stays negligible, but a batched prefill would
   change the shape of the question entirely and nothing here addresses it.
8. **No RTL was written and `llama_top` was not touched**, deliberately: the
   output boundary (section 1.2) is absent, and wiring it is another track's
   file.
9. **`n_rows` is not a multiple of `ROWS_IF` for the last window** (5,056 rows,
   106 tiles, so 32 padding rows in the final tile). The packer zero-fills them
   and the descriptor's `n_rows` bounds the emit, but nothing here **measured**
   that the 32 pad rows produce no logits.

## 11. Decisions that need Oren, not an implementation

1. **`token_embd.weight.mv4i` in HBM.** Under the recommended host gather it is

   own rate) that nothing on the card reads. Drop it, or keep it as
   pre-positioning for a future on-card gatherer. Section 4.4.
2. **Spec D 3.2's recipe.** Section 5 recommends folding the `>> 15` into the

   `sim/regress.sh` is shared and `BASELINE_PASS` moved twice today.

### 2026-08-29: the port arithmetic in sections 1.3 and 11.2 is off by one, and the conclusion is strengthened

**Read at commit `abbd2ed`.**

Sections 1.3 (`:37`) and 11.2 (`:323-326`) both say *"A takes 27 of 30 engine
ports"* with *"3 remain"* for B and C. **WITHDRAWN: it is 28 of 30 and 2
remain.**

The 27 is `rtl/matvec_int4.vhd`'s `NPORTS_W + NPORTS_S = 24 + 3`. The entity
that actually reaches HBM is `rtl/matvec_int4_desc_axi.vhd` (`a4f7e17`), which
carries a **separate descriptor-fetch read master** at `:169-174` beside the
27-wide array at `:182-191`. `hw/fk33/rtl/fk33_engine.vhd:7-8` states the total
in its own header: *"27 weight/scale AXI read masters + 1 descriptor master = 28
masters."* MEASURED. Full write-up:
`docs/2026-08-28_can-27-read-masters-be-served.md`, correction appended the same
day.

**This does not change the recommendation; it makes it stronger.** Section 11.2
argues *"A 28th master for a 0.09% latency saving is the wrong trade."* That
28th master now exists and is spent on something else, so an on-card gatherer
would be the **29th**, against 2 free ports that B and C between them already
want 7 of. The residency map's "real conflict" is one port worse than this
document costed it.

**NOT verified:** whether the descriptor master could share a port with a scale
master given its duty cycle. That is the only obvious route back to 3 free
ports and nobody has costed it.

### 2026-08-29: "the LM head is a 512-entry ROM" no longer describes the 9B path

Not a correction to this document, which is careful about it, but recorded here
because this file is where the LM head question gets read. MEASURED at
