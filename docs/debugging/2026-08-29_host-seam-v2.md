**Date:** 2026-08-29
**Track:** SERVER, backlog item 5
**Files:** `server/**`, plus a one-line guard in `tools/gen_layer_program.py`
**Hardware touched:** **NONE.** No `/dev/xdma*` was opened. See section 9.

## 2. The answer, up front

**The seam moved, and the host half is built and tested against a simulated
card. The card half does not exist and cannot, today: the composed FK33 design
does not route (OI-12), and even if it did, `rtl/llama_top.vhd:133-134` says in
its own words that there is no sampler and no lm_head output -- the final A job
is issued with `dst = R_NONE` and its result is DISCARDED. Nothing anywhere
returns logits to a host.**

Four things landed:

1. **`server/fk33_seam.h`**, the contract: what crosses, in which direction, in
   what units, who owns each piece of state, and an explicit list of what does
   not exist.
2. **`pl_backend` v2** (`server/pl_backend.{h,c}`) over a transport
   (`server/fk33_transport.{h,c}`) with three entry points, of which two are
   the SAME code -- the real `pread`/`pwrite` chardev path, pointed either at
   `/dev/xdma0_*` or at ordinary files. The third is a modelled card
   (`server/fk33_sim.c`). Swapping in the real transport is an argument change.
   v1 is retained for the AXU3EG as `server/pl_backend_axu3eg.{h,c}` with its
   symbols renamed `plv1_*`.
3. **The C tokenizer is linked**, and with it a new C renderer for the Qwen3.5
   chat template (`server/qwen35_chat.{h,c}`), because without the template the
   tokenizer alone cannot produce a correct prompt. The renderer is checked
   **byte for byte against Jinja2 evaluating the model's own template**, and
   its ids against **llama.cpp**: 2,037 of 2,037 cases identical on both legs.
4. **The `mk_shape_scaled` guard**, refusing rather than mirroring, with 16 and
   32 byte-identical to before.

**Two real defects were found, both by an external oracle and neither by any
amount of internal checking:**

- **The trailing UTF-8 trim was wrong.** `utf8_back()` tested `s[i-n]` starting
  at `n = 1`, so it examined the byte *before* the last one and never the last
  one itself. Leading U+00A0 was stripped; trailing U+00A0 was not. Both halves
  of the function were self-consistent. Caught on the FIRST run against Jinja2,
  on 6 of 47 hand-written cases.
- **The renderer's return contract was ambiguous.** `-(bytes needed)` and the
  `QWEN35_CHAT_E_*` refusal codes shared the negative half-line, so a 4-byte
  render returning `-4` was indistinguishable from `QWEN35_CHAT_E_TOOLS`.
  Caught by writing the batch driver against it, which is to say by making
  something else consume the API.

## 3. The procedure, in the order it was run

Each step names what it isolates.

| # | step | isolates |
|---|---|---|
| 1 | read `server/pl_backend.{h,c}`, `llama_server.cpp`, `hw/fk33/host/fk33_bringup.c`, `hw/fk33/host/fk33_regs.h`, `hw/fk33/rtl/fk33_engine.vhd`, `rtl/matvec_int4_desc_axi.vhd`'s map | what the code says, before any document |
| 2 | a subagent read the six seam documents and reported contradictions | what the documents say, and where they disagree with each other |
| 3 | write `fk33_seam.h` first, before any implementation | forces every open question to be named rather than coded around |
| 4 | implement the transport with the chardev path FIRST, then point it at files | makes "the real transport" the thing that is written, not the thing that is deferred |
| 5 | implement the sim as the HARSHEST legal card | a test double that is lenient hides the host's bugs |
| 6 | `server/tests/seam_selftest.c`, then 10 mutations of the PRODUCTION code | whether the test can fail at all |
| 7 | write the chat renderer, then `server/verify_chat_template.py` against Jinja2 | whether the transcription is right, independently of its author |
| 8 | add the llama.cpp id leg | `parse_special`, which leg 1 structurally cannot see |
| 9 | 9 mutations of the renderer | the resolution floor of legs 1 and 2 |

Steps 3 and 4 are the two that mattered. Writing the header first turned "the

### 4.2 Seam mutations. `n failed` is out of 74 checks

Every mutation is applied to the PRODUCTION source, not to the test.

| id | mutation | result |
|---|---|---|
| M1 | `push_x` writes at stride `x_stride - 64` | **BITES** 15 failed |
| M2 | mantissas written at header offset +8 instead of +16 | **BITES** 25 failed |
| M3 | activation buffer filled with `0xA5` instead of zeroed | **BITES** 25 failed |
| M4 | `seam_wait` polls `done` only, not `(done \| err)` | **BITES** 3 failed |
| M5 | `fk33_seam_check_blocks` drops the stack-straddle return | **BITES** 2 failed |
| M6 | `pl_prefill` stops splitting into chunks | **BITES** 4 failed |
| M7 | remove ONLY the `logit_exp` header/register cross-check | **DOES NOT BITE** |
| M7b | remove ONLY the `argmax` header/register cross-check | **DOES NOT BITE** |
| M7c | remove BOTH | **BITES** 1 failed |
| M8 | the sim sets `done` alongside `err` | **BITES** 1 failed |

**M7 and M7b are the most useful rows here.** The two cross-checks are
REDUNDANT against the one fault that exercises them (`fault_stale_argmax`
desynchronises both the exponent and the argmax at once), so removing either
alone is invisible and only removing both is caught. That is the resolution
floor of T7(c): it can see "the register block and the DMA'd row disagree", not
"they disagree in field X". A fault that moved only one field would need its
own injector.

M4's three failures are worth naming, because they are exactly the trap the
descriptor-format document warns about for subsystem A:

```
  FAIL: err-on-go not reported   (tests/seam_selftest.c:258)
  FAIL: wrong error code 0       (tests/seam_selftest.c:259)
  FAIL: ERR_INFO not carried     (tests/seam_selftest.c:261)
```

A done-only poller does not merely miss the error, it waits out the full
timeout on every failure and then reports the wrong thing.

### 4.4 The defect the oracle found on its first run

```
  case 18: agp=1 think=0 msgs=[{'role': 'user', 'content': '\xa0padded\xa0'}]
    jinja2 : b'<|im_start|>user\npadded<|im_end|>\n<|im_start|>assistant\n<think>\n\n</think>\n\n'
    C      : b'<|im_start|>user\npadded\xc2\xa0<|im_end|>\n<|im_start|>assistant\n<think>\n\n</think>\n\n'
    first difference at byte 23: b'<|im_end|>\n<' vs b'\xc2\xa0<|im_end|>'
```

Six of 47 hand-written cases: U+00A0, U+2028 and U+3000, each in a user and in
a system message. Leading whitespace was stripped correctly in all six; only
trailing was wrong. The fix is one index:

```c
-    while (n < 4 && i >= n + 1 && ((unsigned char)s[i - n] & 0xC0u) == 0x80u)
+    while (n < 4 && n - 1 <= i && ((unsigned char)s[i - (n - 1)] & 0xC0u) == 0x80u)
```

### 4.5 Chat-template mutations, out of 2,037 comparable cases

| id | mutation | result |
|---|---|---|
| `think-default` | swap the two `add_generation_prompt` thinking branches | **BITES** 1045 differ |
| `ascii-trim` | trim ASCII whitespace only | **BITES** 1208 differ |
| `user-newline` | drop the newline after a user turn's `<\|im_end\|>` | **BITES** 2037 differ |
| `last-query` | `i >= last_query_index` instead of `i >` | **DOES NOT BITE** |
| `last-query-default` | skip the reverse scan, take the template's default `len-1` | **BITES** 836 differ |
| `think-split` | body split on the FIRST `</think>` instead of the last | **BITES** 95 differ |
| `reason-trim` | do not trim the extracted reasoning | **BITES** 36 differ |
| `system-twice` | emit the system turn in the body loop as well | **BITES** 612 differ |
| `no-special` | tokenize with `parse_special = 0` | **BITES** 340 of 340 ids |

**`last-query` cannot bite, and that is a proof rather than a coverage gap.**
`last_query_index` is by construction the index of a USER message; a user
message takes the user branch and never reaches the assistant branch where the
comparison lives; and the one message list with no user index at all raises
`NOQUERY` instead. So `>` and `>=` are equal on every reachable input. It is
kept in the table under its own name, and `last-query-default` was added
alongside it as the mutation that actually probes the `multi_step_tool` scan.

**`no-special` did not bite on its first run, and the reason was the harness,
not the check.** `tests/chat_batch.c` was calling `qwen35_tok_encode` directly
instead of the shipped `qwen35_chat_tokenize`, so the mutated line never
executed. That is the classic "the harness does not run the code under test"
defect. It is recorded here rather than quietly fixed; after pointing the
driver at the shipped API it bites on 340 of 340.

## 5. Measured and REJECTED. Do not retry these

**Returning logits over the AXI-Lite BAR.** Subsystem A's only numeric egress
today is `Y_IDX`/`Y_LO`/`Y_HI`/`Y_EXP`, four non-posted BAR accesses per result
row. At `n_vocab` 248,320 that is 993,280 reads; at the 1-2 us per BAR read
`docs/2026-08-28_token-io-path.md` estimates, **1.0 to 2.0 seconds per token**
against a 38.27 ms budget. It is not a slow seam, it is not a seam. The logits
must land in HBM and come back by C2H, and the RTL for that does not exist.

**Sizing the logits path from the PCIe bring-up plan's own table.** That table
(`docs/2026-08-27_pcie-host-bringup-plan.md` section 7.1) uses `151,936 x 2` =
304 KB for "full logits fp16". Both numbers are wrong for this design:
llama.cpp reports 248,320 for this GGUF (section 4.3) and the card's result
rows are int32, not fp16. The real figure is 993,296 bytes, **3.3x** the
table's. A design sized from that row would be 39% short on the vocabulary
alone.

**Mirroring the VHDL's `attn_hd > 32` branch into the Python.** Rejected in
favour of a refusal, on TOP-KV's recommendation and for a stated reason: the
VHDL branch above 32 is a DIFFERENT SHAPE from the one every published landmark
was measured at, nothing generates at `attn_hd 64` today, and an unverified
Python transcription of it would be a second unchecked claim rather than a
check. The refusal names the branch and says what to do if it is ever needed.

**A single `pl_backend` API serving both boards.** Considered and rejected. v1
and v2 disagree about who owns the loop, which is not a parameter. They are two
files, symbols `plv1_*` and `pl_*`, chosen once at startup by flag -- the same
resolution `rtl/matvec_int4_axi.vhd` and `rtl/matvec_int4_desc_axi.vhd`
already use, and for the same reason.

**Building an embedding gather here.** Backlog item 5 depends on item 4 for a
real vocab path, and item 4 owns `rtl/` and `tools/`. What landed instead is
the interface (`pl_embed_fn`) plus one deliberate non-implementation
(`pl_embed_synthetic`) that logs a warning on every use. Note the token-I/O
document's MEASURED correction to the dequantize recipe -- folding the `>>15`
into the BFP pack's own shift moves mean relative error 0.22794 -> 0.08630, a
factor of 2.641 -- which is the thing whoever writes the real one must not
re-derive from spec D 3.2 as written.

**Building a competing 9B numeric reference.** Explicitly out of scope; TRACK
REF9B owns it. The interface this track would consume is
`fk33_sim_opts.logits_fn`, and it is one function.

## 6. Measurement traps hit, including my own

**A `>` in a shell redirect can fail before the program runs, and the exit
status is the redirect's.** The first attempt to re-run the `attn_hd` 16/32
comparison printed `hd=16 rc=1` and `hd=32 rc=1` and looked like the guard had
broken the working cases. It had not: the output directory did not exist, bash
failed the `>` redirect, and the `rc=$?` captured the shell's failure, not
`gen_layer_program.py`'s. **The tool was never invoked.** Fixed with a `mkdir
-p`; recorded because "the tool now fails on the case it used to pass" is
exactly the shape of a real regression and it was a shell error.

**Relative paths after `cd` inside a compound command.** The first attempt to
reproduce the pre-guard `attn_hd 64` trap ran `python3
tools/gen_layer_program.py` from a scratch directory and got `can't open file`.
Harmless here, but it produced an `rc=2` in a table of `rc=0`/`rc=1` values
that mean something else.

**A mutation that does not bite may be testing nothing at all.** The
`no-special` mutation reported DOES NOT BITE, which reads as "the check is
blind to `parse_special`". It was not: the batch driver was calling the
tokenizer directly rather than the function the mutation edits, so the mutated
line was never executed. **A mutation result is only meaningful once you have
confirmed the mutated line is on the path the harness takes.** The
distinguishing evidence is cheap -- after pointing the driver at the shipped
API, 340 of 340 differ, which no genuinely blind check would produce.

**`StrictUndefined` makes the oracle wrong, not strict.** The first run of
`verify_chat_template.py` reported "167 of 247 cases accepted by C only", i.e.
the C rendering things the template refuses. Every one was the harness: the
template reads `message.tool_calls` and `message.reasoning_content` on every
assistant turn, and under `StrictUndefined` an ordinary message dict without
those keys raises. transformers uses the DEFAULT `Undefined` with
`trim_blocks`/`lstrip_blocks` on, and the environment now matches that
exactly. **An oracle configured differently from the reference implementation
is not an oracle**, and the failure it produces points at the subject.

**74 checks passing on the first run is a reason to distrust the checks.** The
seam self-test did, which is why section 4.2 exists. Two of the ten mutations
turned out not to bite.

## 7. Contradictions between the documents and the code, named

The code wins in all of these, per the house rule.

1. **The descriptor base array: mandatory, or unnecessary?**
   `docs/2026-08-28_matvec-descriptor-format.md` makes 24 weight + 3 scale
   64-bit bases a byte-pinned part of every descriptor with `ERR_GEOM` if the
   count is wrong. `docs/2026-08-27_hbm-residency-map.md` section 5 says that
   array "does not need to exist", replacing it with one `w_off` plus a
   compile-time arena table. `rtl/matvec_int4_desc_axi.vhd` implements the
   first. The residency map's simplification is **withdrawn in practice and
   never marked withdrawn.**

2. **The HBM layout: 27 arenas, or flat contiguous?** The residency map places
   27 lane arenas of 160 MiB with `kv_bytes_per_token = 17,408` and
   `max_context = 198,415`. The manifest that was actually packed and loaded is
   flat contiguous with `kv_bytes_per_token = 65,536` and
   `max_context_tokens = 52,756`. **The manifest is the one whose bytes are on
   the card.** `pl_open_opts_default`'s block addresses are placeholders for
   exactly this reason and say so.

3. **The shipped weight image already straddles the HBM stack line.**
   `blk.7.ffn_gate.weight` spans `4,267,130,880..4,295,446,528`; the boundary
   is `4,294,967,296`; its last 479,232 bytes are on the wrong side. The
   residency map names that class as a silent wrong answer. This is a live
   defect in the image, not in the seam, and it is why
   `fk33_seam_check_blocks()` exists and runs before any DMA.

4. **`server/README.md` and `server/Makefile` both said the Qwen3.5 seam was
   blocked on the descriptor format AND on rendering the chat template.** The
   first is settled; the second is now `server/qwen35_chat.c`. Both notes are
   updated in place rather than deleted, so the reason they existed survives.

5. **The vocabulary.** Section 4.3.

6. **`docs/2026-08-27_pcie-host-bringup-plan.md` section 7.2's per-token
   protocol is pre-descriptor-plane.** Its step 9 is "MMIO write token id,
   position"; the token-I/O document requires the host to gather, dequantize,
   BFP-pack and H2C-DMA an 8,192-byte activation row, and the audit confirms
   the descriptor program has no embedding opcode. That sketch should not be
   used as the seam.

## 8. Open, not yet answered

- **Does a `y`-to-HBM writeback fit in the fabric?** This is the one question
  that decides whether "decode returning logits" is the right seam at all. If
  it does not, the fallback is argmax-plus-top-k on the card and the host loses
  `top_p`. Nothing measured here can settle it.
- **What is the real per-transfer DMA latency?** Every timing in the seam
  definition applies a 1 GB-transfer rate to a 1 MB transfer, because no
  small-transfer latency has ever been measured on this card. The estimates are
  optimistic by an unknown amount.
- **Why is C2H one third of H2C?** Recorded as unexplained at first light. The
  logits path is the first thing that cares.
- **Where does `x_exp` come from?** Three candidate homes now: A's descriptor
  extension word 2, the wrapper's `x_exp` port under `USE_XEXP_PORT`, and this
  seam's activation header. That is an integration decision.
- **What BAR offset does the seam block get?** Only `hw/fk33/gen_pcieep.py` can
  say. `0xE000` is a proposal chosen from the measured holes.
- **Is one shared logits exponent enough dynamic range across 248,320 rows?**
  It is forced by RAW `out_mode` and it is what the lm_head windowing already
  relies on, but nothing here measures the resulting quantization of the
  softmax at temperature.

## 9. NOT verified. Read this before quoting anything above

- **NOTHING WAS RUN AGAINST THE CARD.** No `/dev/xdma*` was opened, no
  bitstream was programmed, no `xsdb`, `hw_server`, `pcieep.sh`, `jtag.sh`,
  `flash.sh` or `program.tcl` was invoked. `fk33_transport_open_chardev()`
  refuses a `/dev` path without an explicit `FK33_ALLOW_HARDWARE` token that
  nothing in this tree passes, `llama_server --card` accepts only `sim` and
  `file`, and `seam_selftest` T12 asserts the refusal.
- **No token produced by the Qwen3.5 arm is inference.** The simulated card
  does not run a transformer, its logits are a synthetic function by
  construction, and the embedding provider is synthetic too. The server says
  this in its banner, in `/v1/models`, and in a warning per open.
- **The seam register block, its BAR offset, its error codes and the two byte
  layouts are PROPOSALS.** No RTL implements them.
- **`fk33_sim.c` does not model subsystem A.** The descriptor is checked for
  presence and alignment and otherwise not executed.
- **The chat renderer covers a SUBSET** and refuses the rest: `tools`, the
