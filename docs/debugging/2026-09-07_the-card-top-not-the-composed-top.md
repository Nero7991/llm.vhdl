# The BD cell is `fk33_llama_top`, not `compose4_top`, and it elaborates with both HBM memory subsystems on

**Date:** 2026-09-07
**Question:** the wrapper made `compose4_top --wire --mem` packager-legal, but
that top exports 1,300 ports of which about 450 are loose internal seams. A
block-design cell with 450 unconnectable ports is not viable. What is?

## The answer, up front

**`rtl/fk33_llama_top.vhd`, which was the card top all along.**

| | ports | packager refusals |
|---|---|---|
| `compose4_top --wire --mem` | 1,300 | 57 |
| **`fk33_llama_top`** | **141** | **4** |

It terminates its own seams and exposes exactly the four master groups the port
budget is about: `a_*` (subsystem A), `bst_*` (B's recurrent state),
`kv_*` (C's KV cache) and `m_*`. The four refusals are the host region-file
window (`hw_reg`, `hw_addr`, `hr_reg`, `hr_addr`), all `natural range`.

Wrapped by `tools/gen_bd_wrapper.py` it is **141 ports, 0 refusals, and no
generic clause at all** -- the packager gets a cell with nothing to infer --
and it **ELABORATES in Vivado with zero errors** at

```
--generic B_STATE_AXI=true --generic C_KV_AXI=true --generic C_KV_BLOCK=32
CARD_ELAB_OK bitports=3588
```

**Nothing had elaborated that combination before.** `B_STATE_AXI` and
`C_KV_AXI` both default to `false`, and every prior measurement of the composed
design was taken with both HBM memory subsystems absent entirely.

## I was working on the wrong top, and the tell was in the port count

`compose4_top` is a **co-residency measurement vehicle**: one synthesis top
carrying A, B, C and D so the composition can be placed rather than summed. Its
header says exactly that. It exports every internal seam **on purpose**, so
that synthesis cannot optimise anything away.

`fk33_llama_top` is the **card top**, generated by `tools/gen_cardtop.py` from
`rtl/llama_top.vhd`. It contains the same subsystems wired to each other.

The 1,300-versus-141 gap was visible from the first measurement and I spent the
BD analysis on the larger number anyway, because I had started from the
composed top for the FIT question -- where it is the right vehicle -- and
carried it into the BD question, where it is not. **The vehicle that answers
one question is not automatically the artefact that ships.**

## Three configuration facts found by doing it

- **`A_NPORTS = 5`**, a constant in `rtl/llama_map_pkg.vhd`. The card top's
  subsystem A presents **five** HBM read ports, not `fk33_engine`'s **28**.
  Those are two different configurations of A and the port budget must say
  which it means.
- **`C_KV_BLOCK` defaults to 4, and `attn_kv_axi` asserts `KV_BLOCK >= 16`.**
  So `C_KV_AXI=true` at the default is not a legal configuration; the card must
  pin 32. This is the same three-way geometry constraint recorded in
  `llama_top`'s `C_KV_AXI` declaration, biting from the other side.
- **`synth_design -rtl` cannot dissolve B's `zb_reg`**, 196,608 bits.
  `[Synth 8-3391]` names the remedy itself. It is an ELABORATION limit and says
  nothing about whether that array becomes a BRAM in real synthesis.

## A silent-wrongness bug in the wrapper generator, fixed and then teeth-tested

The wrapper declares no generics, so every port width must be folded to a
literal. The first version folded using the entity's **default** generic
values -- while `--generic` pinned the INSTANCE to different ones. Pinning
`C_KV_BLOCK=32` while folding widths with 4 would give an entity whose port
widths do not match the instance behind them, **and nothing would error**,
because both halves are individually well-formed VHDL.

This is `CLAUDE.md`'s recorded hazard, *"a generic that must agree with a
derived value is a new way to be silently wrong"*, arriving in a new place.

Fixed so a pinned generic drives the folding. **Then teeth-tested, and it does
NOT bite here**: generating at `C_KV_BLOCK=4` and at `32` gives a
byte-identical port clause, **0 diff lines**, because no port width depends on
it. Recorded under its own name because a non-biting check measures the
resolution floor: the fix is right in general and unnecessary for this entity,
and only the diff distinguishes those two states.

## Measurement traps hit

- **Six `[Synth 8-36] 'step_w' is not declared` errors** naming signals that
  look like they should exist. Cause: the first wrapper passed through widths
  that reference the ENTITY's generics, which the wrapper does not have. The
  error names the symbol, not the reason.
- **`tail -2` hid the diagnostic that would have confirmed a fix was running.**
  I concluded the fix had not landed and went looking in the source. It had;
  my own output filter cut the line.
- **An `export` after the heredoc that reads the variable.** `KeyError: 'SPX'`,
  and the Vivado run that followed used the OLD script and reproduced the
  previous error exactly -- which reads as "the fix did not work".
