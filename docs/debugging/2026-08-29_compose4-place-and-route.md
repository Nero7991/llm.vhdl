## 1. What was built, and the one thing it deliberately does not do

`hw/fk33/rtl/compose4_top.vhd`, generated by `hw/fk33/gen_compose4_top.py`
(commit `847ebdb`), is the first RTL top in this project that carries all four
subsystems for the card:

| instance | entity | what it is | generics |
|---|---|---|---|
| `a_eng` | `fk33_engine` | subsystem A, the SHIPPING wrapper, byte-for-byte the entity in the bitstream on card 1 | it has none |
| `b_gdn` | `gdn_block` | subsystem B, Gated DeltaNet | all defaults |
| `c_attn` | `attn_block` | subsystem C, gated attention | `HEAD_DIM=256 N_QH=16 N_KVH=4 LAYERS=8` |
| `d_fetch` | `seq_desc_fetch` | D, descriptor fetch | all defaults |
| `d_opdec` | `seq_opdec` | D, opcode decode | all defaults |
| `d_lock` | `seq_region_lock` | D, region lock | all defaults |
| `d_viss` | `seq_vec_issue` | D, vector issue | all defaults |
| `d_vres` | `seq_vec_res` | D, vector result | all defaults |
| `d_norm` | `ooc_normadapt` | D's vector arithmetic: `llama_top`'s `gvr` adapter, containing `rmsnorm_rs` at N=4096 | all defaults |

Every generic is exactly the one the corresponding row of TRACK DISTRAM's
217,381 booking was measured with, so the composed number is comparable to that
booking without adjustment. `ooc_normadapt` is itself generated, by TRACK
NORMADAPT's `sim/ooc_normadapt_extract.py`, from `rtl/llama_top.vhd` at the same
pinned SHA.

**The nine instances share `core_clk` and `core_rst` and are NOT wired to each
other.** `fk33_engine` additionally takes `hbm_aclk`, the second domain the card
runs. Every other port of every instance is a top-level port: 1,184 port
declarations, 36,529 bits.

That is the deliberate limit. **How the subsystems are wired to each other and
to the host is board row N2, and N2 is a decision reserved for Oren.** Wiring
them would be picking it. So:

* This establishes **fit, placement, routability and timing**.
* It establishes **nothing about arithmetic**. A routed design is not a correct
  one, and subsystems B and C have never run on this silicon at all.
* It excludes inter-subsystem nets, and it excludes the FK33 shell.

### Why the ports go to the top level rather than into a stimulus harness

A harness that drove the wide inputs from an LFSR and XOR-reduced the wide
outputs would add its own LUTs and FFs to the very number this exists to
measure, and they would then have to be measured and subtracted: a second
measurement with its own error, on top of the one being reported. An
out-of-context port costs no cells and cannot be optimised away, so the cell
count is the subsystems' own. The price is paid in `report_route_status`, and
section 4 says exactly what that price is and how it is counted.

## 3. The procedure, in the order it was run

Each step says what it isolates.

1. **Reconcile the booking against the artefacts, not against a summary.**
   The brief warned that two prior bookings were stale and that it had relayed
   both. Every row in section 2 was read out of the CSV that produced it, and
   the generics were read out of the CSV's own `gen` column, not out of any
   write-up's prose. *Isolates: quoting a number whose provenance has drifted.*

2. **GHDL analysis of the composition, as a cheap structural check.**
   *Isolates: entity/port binding errors, before an hour of Vivado.* It found
   one thing and it was my own error; see the traps section.

3. **A four-flop BUFG probe.** *Isolates: whether an out-of-context flow gives
   the design a global clock at all.* It does not, and this changed the RTL.
   Section 4.

4. **`synth_design -rtl` elaboration only.** Minutes rather than an hour.
   *Isolates: every remaining binding, width and visibility error in a
   2,495-line generated file.* Clean: **631,988 RTL cells, 36,529 ports, zero
   `ERROR` lines, 96 of 96 RTL files read with no `READ_SKIP`.*

5. **Full out-of-context synthesis, checkpointed.** *Isolates: the composed
   area with cross-boundary optimisation ALLOWED, which the booking's
   `-flatten_hierarchy none` forbade.*

6. **`opt_design` + `place_design` + `phys_opt_design` + `route_design` inside a
   `pb_core`-shaped pblock.** *Isolates: whether the composition fits and routes
   in the region the shipping floorplan reserves for compute.*

7. **The same, unconstrained on the whole die.** *Isolates: whether a failure in
   step 6 is a REGION failure or a DEVICE failure. Those are different findings
   and the fixes are different.*

The two implementation runs share one synthesis checkpoint, so any difference
between them is placement and routing and nothing else.

## 4. MEASURED: an out-of-context flow will not give you a clock buffer, and the obvious fix is not the fix

This changed the RTL, so it is stated before the results.

A four-flop probe (`hw/fk33/results/compose4_2026-08-29/bufg_probe.vhd`,
`bufg_probe.tcl`) on this part:

    PROBE_A_BUFG 0            plain synth_design -mode out_of_context
    PROBE_A_NETTYPE LOCAL_CLOCK
    PROBE_B_BUFG 0            ... plus an out-of-context XDC carrying
                              set_property CLOCK_BUFFER_TYPE BUFG [get_ports clk]

So neither the flow nor the documented property inserts one. And setting that
property **before** `synth_design` in a non-project in-memory flow does not
merely fail to work, it **errors**, because there are no port objects until
synthesis has run:

    ERROR: [Common 17-161] Invalid option value '' specified for 'objects'.

A 300,000-load clock left on `LOCAL_CLOCK` routing would make every placement,
routing and timing number that followed meaningless -- and it would do so while
the run still completed and printed numbers. So `compose4_top` instantiates
`BUFGCE` itself, and `sim/ooc_compose4_pnr.tcl` **aborts** after synthesis if it
does not find two of them. The abort is a Tcl `error`, not an
`assert ... severity failure`, because Vivado silently ignores the latter in
synthesis.

### 5.1 The composed synthesis, and the first thing it settles

MEASURED, `synth_design -mode out_of_context -top compose4_top`, default

                      carry8 12147  f7 65108  f8 25788  bram 246.5  uram 0

    C4_BUFG 2

`report_utilization -hierarchical`, per instance, against the row of the
booking each instance corresponds to:

| instance | entity | booking LUT | composed LUT | delta |
|---|---|---:|---:|---:|
| `b_gdn` | `gdn_block` | 75,297 | 75,181 | -116 |
| `c_attn` | `attn_block` | 85,816 | 85,592 | -224 |
| `d_fetch` | `seq_desc_fetch` | 702 | 509 | -193 |
| `d_opdec` | `seq_opdec` | 262 | 229 | -33 |

| | **total** | | **350,283** | |

**TRACK DISTRAM's 217,381 was right to within 0.80%, and it was right in the
CONSERVATIVE direction.** That is worth stating plainly, because the brief
warned that "tonight's per-module projections were optimistic on **every** row
before they were measured". This one was not. Composing the eight units into
one synthesis, with the cross-boundary optimisation their `-flatten_hierarchy
none` runs forbade, bought **1,731 LUT, 0.80%** -- and one row (`seq_region_lock`)
went the other way by 9.

The other columns agree even more tightly:

* **DSP: 2,177 MEASURED, 2,177 DERIVED.** Exact.
  1,585 (A, and the same 1,585 the routed shell build reports) + 253 (B) +
  298 (C) + 41 (`ooc_normadapt`) + 0 (the five `seq_*`).
* **FF: 355,468 MEASURED against 355,236 DERIVED** (291,516 for B+C+D plus
  63,720 for A's routed engine), +232, 0.07%.
* **BRAM tile: 246.5**, of which A 192.5, B 43, C 11. B's and C's are the
  booking's 43 and 11 unchanged.
* **URAM: 0.** Nothing in the composition uses a single URAM.

So the sum-of-seven-independent-runs model of this design's area is sound, and
the correction it needs is smaller than the noise anyone would have allowed for
it. **What it was NOT sound about is timing, and section 5.3 is where that
lands.**

### 5.2 What the total means against the two budgets

Two numbers here are MEASURED from the shipping routed build and one is
DERIVED; the arithmetic is shown so it can be checked.

    composed, post-synthesis, MEASURED                    350,283
      device CLB LUTs                                     439,680     79.67%

    the FK33 shell WITHOUT the engine, DERIVED from
    e2e_util_routed.rpt 171,458 minus
    e2e_engine_util_routed.rpt 131,132                     40,326
    composed + shell, DERIVED                             390,609     88.84%

    plus a real NORM_W_IMAGE, MEASURED by TRACK NWROM      32,943
    the honest total for a build that can actually run    423,552     96.33%

**96.33% of the device's CLB LUTs.** That is the number the schedule should be
read against, and it is not the 217,381 that has been circulating, because
217,381 excludes subsystem A, excludes the shell, and excludes the gain image.

Two caveats on that arithmetic, both stated because they cut opposite ways:

* It adds a post-SYNTHESIS composed number to post-ROUTE shell numbers.
  Implementation shrinks LUTs: A's own engine is 134,633 post-synth here and
  131,132 post-route in the shipping build, **-2.6%**. Section 5.3 replaces
  350,283 with the routed figure.
* It assumes the shell's 40,326 LUT is unaffected by having 2.7x more logic
  beside it, which is true for cell count and false for routing.

**And section 5.3 shows that the whole of this subsection is asking the wrong
question, because LUTs are not what runs out.**

### 5.3 Placement, and the resource that actually binds

`opt_design` moved almost nothing: **350,283 -> 350,228 CLB LUT, -55**, in 171 s.
`place_design` took **1,638 s** and brought it to **346,971**. Then the row that
matters:

    C4_UTIL c4dev placed  lut 346971  lut_logic 331916  lut_mem 15055
                          ff 356525  carry8 12147  f7 65108  f8 25788
                          bram 246.5  uram 0  dsp 2177  clb 54866

**`clb 54866`. The device has 54,960. That is 99.83%, with 94 CLBs left on the
whole die.**

**The binding resource is not the LUT, it is the CLB, and every budget in
circulation for this design is denominated in the wrong unit.** At 346,971 LUT
the design is at 78.9% of the 439,680 CLB LUTs and looks like it has a fifth of
the device spare. It has 94 CLBs.

The reason is packing density, and it is MEASURED on both designs:

    shipping build, routed   171,458 LUT in 30,705 CLB  =  5.58 LUT per CLB
    compose4, placed         346,971 LUT in 54,866 CLB  =  6.32 LUT per CLB
    the architectural maximum                              8.00 LUT per CLB

A CLB holds 8 LUTs, but a design carrying **65,108 F7 muxes and 25,788 F8
muxes** cannot use them all: an F7/F8 mux pair fixes which LUTs must sit
together, and Vivado places those as indivisible shapes. The composition has
90,896 of them. That is what spends CLBs faster than LUTs, and both `attn_block`
and `ooc_normadapt` are full of the wide multiplexers that create them.

**DERIVED, and it is the number to plan against: at 6.32 LUT per CLB this device
holds about 347,000 LUT of THIS design's logic, not 439,680.** The composition
is already there. The shell's 40,326 LUT and NWROM's 32,943-LUT gain image do
not fit in 94 CLBs, and neither does either one alone.

## 7. Measurement traps hit, including my own

1. **`ghdl -a` without `-frelaxed` reports a hard error inside
   `rtl/attn_block.vhd` -- and the file is fine.** `rtl/attn_block.vhd:396`
   declares `constant G`, and `:1022` opens `gqpl : for g in 0 to G-1 generate`.
   VHDL is case-insensitive, so `g` and `G` are the same identifier and the
   generate parameter hides the constant inside its own range expression. Bare
   `ghdl -a --std=08` prints

       attn_block.vhd:1022:14: warning: declaration of "g" hides constant "g"
       attn_block.vhd:1022:24: constant "g" is not visible here
       attn_block.vhd:1026:19: no function declarations for operator "="

   and **returns rc 0 while doing it**, which is the documented mcode trap in
   this project's CLAUDE.md. `sim/regress.sh:374` passes `-frelaxed`
   unconditionally, and with it the same command reduces to the one `-Whide`
   warning and nothing else. **This was my trap, not a defect**: I ran GHDL
   without the gate's own flags and then spent time deciding whether subsystem C
   had a simulation problem. It does not. The name collision is still worth
   knowing about, because it is exactly the shape of thing that reads
   differently in two tools.

2. **`ghdl -m` returned rc 0 with four hard-error lines on its stdout.**
   Same trap, same run. Never gate on GHDL's exit code.

3. **A 2-minute tool timeout is not a Vivado timeout.** The first attempt to run
   the elaboration check died at exactly 120 s and looked like a Vivado failure.
   It was the shell wrapper. Every Vivado invocation here is detached, under
   `systemd-run --user`, and gated on a printed sentinel.

4. **`vivado` is not on `PATH` by default in this environment.** The first
   launch returned `rc=127`, `No such file or directory`, which reads like a
   crash rather than a missing binary. It is at
   `/tools/Xilinx/2023.2/Vivado/2023.2/bin/vivado`.

5. **A strict "wait until no other vivado is running" gate can cost an hour to
   nothing.** Three other tracks were synthesising. TRACK NORMADAPT's
   bounded-patience pattern was reused rather than reinvented, and the patience
   was lowered from 3600 s to 900 s once it was clear the other track was
   running many short points back to back -- which is the exact livelock
   NORMADAPT recorded.

## 8. What was NOT verified

**Arithmetic. None of it.** This document establishes fit, placement,
routability and timing, and it establishes nothing whatever about whether the
composition computes correct numbers. Subsystems B and C have never run on this
silicon. `compose4_top` does not wire the four subsystems to each other, so
every path measured here is internal to one subsystem, and connecting them can
only add paths.

The remaining items are enumerated in
`docs/debugging/2026-08-30_timing-composed-a-b-c-d.md` sections 11 and 13,
including the one this run did not reach: **the `impl_pb` stage, the placement
constrained to the shipping floorplan's `pb_core`, was never executed.**

## 9. The gate row I would add, and cannot

`sim/regress.sh` is owned by TRACK FLOOR, so this is a handoff, not a change.

**Proposed row `sim:c4gen`.** Regenerate `hw/fk33/rtl/compose4_top.vhd` from
`hw/fk33/gen_compose4_top.py` against a `git archive` of HEAD (plus
`sim/ooc_normadapt_extract.py` to produce `ooc_normadapt_top.vhd` first) and
`cmp` it against the committed file. It is the same guard the project already
applies to `hw/fk33/gen_pcieep.py`'s output, and it costs seconds and no Vivado.

**Its one coupling, stated so it is not a surprise:** the row transitively
depends on `rtl/llama_top.vhd`'s `gvr` generate block, because
`ooc_normadapt_top.vhd` is extracted from it by anchor match. A legitimate
change to that block turns the row red until `compose4_top.vhd` is regenerated.
That is arguably a feature -- it is exactly the drift you want to be told about
-- but it is a shared-file coupling and the owner should decide, not me.
