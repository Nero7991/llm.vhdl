# 32 CRITICAL WARNINGs in the fk33_pcieep block design that are not a fault

**Date:** 2026-08-27
**Hardware / build:** SQRL FK33, `xcvu33p-fsvh2104-2L-e`, Vivado 2023.2,
`hw/fk33/build_fk33_pcieep.tcl` run with `FK33_STOP_AFTER_BD=1`.
No card involved; this is a tool-side finding.

## The question

> Running the PCIe endpoint block design for the first time (`EnablePCIe 1`,
> which has never been built before in this project) emits **32** of these:
>
> ```
> CRITICAL WARNING: [BD 41-1377] Network address <0x0000_0000 [ 256M ]> is
> occupied by different slave segments, </hbm/SAXI_00/HBM_MEM00> in
> </jtag_hbm/Data> and by </hbm/SAXI_16/HBM_MEM00> in </xdma/M_AXI>.
> This is illegal and must be resolved before passing validation
> ```
>
> and then `validate_bd_design` reports success anyway. Is the address map
> wrong, or is the warning wrong?

## The answer

**The warnings are transient and the final map is correct.** They are emitted
*during* the 64-call `exclude_seg_if` sequence, while the map is momentarily
inconsistent, and are never re-emitted once the sequence finishes. The finished
map has `xdma/M_AXI` seeing exactly 33 segments (32 HBM x 256 MB plus the 64 KB
DMA BRAM), `HBM_MEM00` at `0x0` through `SAXI_00`, exactly as designed.

**Consequence for the build script:** grepping the log for `CRITICAL WARNING`
and expecting zero is the wrong check for this design and will read as a
failure on every future build. The right check is that **no** `CRITICAL
WARNING` appears *after* the last `Excluding slave segment` line, plus
`FK33_BD_VALIDATE OK`.

## The procedure that produced it, and what each probe isolates

1. **Run the BD only, not the whole build.** `FK33_STOP_AFTER_BD=1` stops after
   address assignment and `validate_bd_design`. Isolates IP configuration and
   addressing from synthesis and implementation. Peak memory 3.35 GB, elapsed
   about 3 minutes -- against roughly an hour and tens of GB for the full build,
   which is why the hook exists at all.
2. **Compare log line numbers, not log contents.** The decisive probe. It
   isolates "the warning describes the final state" from "the warning describes
   an intermediate state", which no amount of reading the warning text can
   settle.
3. **Read the final map back out of the tool**, rather than reasoning about
   what the excludes should have done. Isolates the actual result from the
   intent of the script.

## Measured and REJECTED -- do not retry

- **"Reorder the excludes so they run before `assign_bd_address`."** Cannot be
  done: `exclude_bd_addr_seg` operates on segments that only exist once they
  have been assigned. There is nothing to exclude before assignment.
- **"Suppress BD 41-1377."** Rejected. It is a real check and it will be the
  thing that catches a genuine overlap when the Aurora or engine masters are
  added later. Suppressing it trades a one-line note now for a silent map
  corruption later.
- **"Assign only the SAXI_00 path and never the SAXI_16 path, so no exclude is
  needed."** Not tried and deliberately not tried on this build: it would be a
  structural change to an address map that is otherwise inherited unchanged
  from the HBM bandwidth work, on the one build whose whole purpose is to
  change exactly one thing (PCIe on). Worth revisiting once the link is proven.

## Measurement traps hit, including my own

- **The warning text asserts its own severity and is wrong about it.** "This is
  illegal and must be resolved before passing validation" is emitted by a check
  that then passes validation four hundred log lines later. Reading the text
  and stopping there produces exactly the wrong conclusion.
- **A count is not a location.** `grep -c "CRITICAL WARNING"` returns 32 and
  says nothing. `awk 'NR>N'` returns 0 and settles it. The build script's
  existing "unmatched constraints should be ZERO" check has the same shape and
  is fine, but this one needed the positional form.
- **My own first parse of the address map printed the wrong column.** Iterating
  `get_bd_addr_spaces` returns slave interfaces as well as master address
  spaces, and slave-side segments have an empty `OFFSET`, so the report showed
  a RANGE where an offset was expected and briefly looked like every peripheral
  was mapped at `0x1000`. Only rows whose space is a master (`/xdma/M_AXI`,
  `/xdma/M_AXI_LITE`, `/jtag_*/Data`) mean anything.
- **This build had never been run at all**, so there was no baseline to compare
  the warning count against. Everything before it set `EnablePCIe 0`, which
  means `xdma/M_AXI` did not exist and none of these warnings could occur. A
  "new warnings appeared" instinct is useless on a first build.
